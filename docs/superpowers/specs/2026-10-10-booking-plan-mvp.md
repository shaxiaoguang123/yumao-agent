# Booking plan MVP contract (2026-10-10)

The user's implementation authorization supersedes the historical Task 1B dependency for unbound drafts only. Task 0 remains PARTIAL; Task 1B remains BLOCKED.

A single BookingPlan/PlanRevision system stores kind=unbound_draft. Accepted intent fields: target_date (exact ISO, no past dates on save), preferred_start_times (1..8 unique HH:MM strings, explicit priority order), duration_minutes (30..240, step 30), venue_preference (1..200 trimmed Unicode characters), court_preferences (0..16 unique ordered manual strings, each 1..100), fallback_policy (allow_any_court_in_venue, allow_time_shift, allowed_start_time_range), price_ceiling_minor (nullable exact integer 0..9007199254740991, configured currency required). Empty courts require same-venue fallback. A time range must include all preferred starts and remain within the same local day including duration. These limits describe draft input, not upstream capabilities.

Server-owned context: timezone_name, currency_code, currency_minor_unit_exponent, preference_verification=unverified_manual, catalog_version=null, venue_binding=null. Snapshot includes kind, intent and context; canonical UTF-8 compact sorted JSON plus SHA256. New plans use active context; edits preserve the stored context. Historical revisions are never reinterpreted. No client context or upstream fields accepted.

Schema 5 adds booking_plans and booking_plan_revisions; deferred composite current-pointer FK includes revision number to enforce version/pointer consistency and tenant ownership. Immutable revisions guarded against UPDATE/DELETE. BEGIN IMMEDIATE serializes writes. Stale base_version returns 409 before validation/no-op; identical normalized content at a current version is a no-op. All service reads and mutations bind user_id.

GET/POST /api/plans, GET/PATCH /api/plans/:id, GET /api/plans/:id/revisions; POST/PATCH receive {intent} and {base_version,intent}. 16 KiB JSON limit, duplicate/unknown fields and nonstandard JSON rejected; field errors use safe fixed messages. GET /api/plans/options reports catalog_status=not_configured with empty venues and active context. GET /api/booking-window accepts only target_date (optional default D+2). Response includes existing pure calendar policy plus can_query_upstream=false, can_create_job=false; can_book/can_pay=false. Calendar eligibility never grants upstream access.

Vue JavaScript Composition API: thin PlansView, feature container/composable, form, window status and history components. Reuse existing tokens/navigation/session. List/create/edit/history, explicit time priority controls, manual court input, fallback and exact decimal conversion. 409 preserves draft; latest preview is separate; adopting latest requires an explicit button. Async results fenced by session identity/epoch and request sequence; leave no drafts or late results after account/session changes. All writes serialized in UI; unknown save outcome is shown without automatic retry.

Verification: schema/transaction/isolation/concurrency tests; API security, type/body/date tests; Vitest CRUD/conflict/session/race/price; existing full Mock E2E; new real Flask/SQLite browser runner on fresh temporary resources with denied upstream transport and external browser network. Actual CUA operation and screenshots at 1440x900, 390x844, and narrow overflow 320px.

Future formal binding requires reviewed authoritative VenueCatalog and explicit conversion producing a NEW revision through PlanService. No automatic string matching, IDs, booking type, Job/Worker/payment/Agent or live availability in this MVP. No real DB migrations this run.
