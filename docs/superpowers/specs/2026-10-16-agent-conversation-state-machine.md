# 上下文驱动的预约队列 Agent

更新：2026-10-21
实现：`backend/ai/queue_graph.py`、`queue_policy.py`、`queue_turn.py`、`queue_updates.py`、`planning.py`

## 目标与职责

Agent 将用户的自然语言整理为可核对的候选队列。每轮模型读取整段对话和规范化事实，判断队列意向或即时执行请求，回答问题、抽取/纠正多个字段，并从当前活动缺口中选择下一项。服务端负责验证模型提出的事实，决定状态是否真正完整，并生成候选。Agent 不持有查询场地、预约、下单、支付或保存队列的工具。

设计采用“模型编排，服务端校验”：模式/日期前置、时段/场地依赖、重叠确认、日期范围、时长、营业时间、场地范围和候选上限是硬门槛；2小时优先于1小时是工作流优先级，模型可根据用户当前关注点在依赖满足的活动字段间选择。

## 用户流程策略

1. 先明确只抢2小时、只抢1小时或两者都抢。
2. 再确认有效目标日期。
3. 逐组补全活动时长的时间和场地；通常先2小时，再1小时。每组的场地必须在该组时段有效、重叠解决后确认。
4. 模式未明确、日期无效、活动字段缺失/歧义/无效或候选超过32项时，只能继续对话，不能生成预览。
5. 所有活动字段有效且候选不超过32项时生成预览；只有用户点击“确认并保存队列”才写入人工队列。

1小时和2小时完全独立，不互借时段或场地。选择单一时长后，另一组不进入候选；模型会说明该组字段被排除。候选时段只能是完整1小时或2小时、整点、09:00–22:00；场地仅1–10号；重叠要明确处理。

## 每轮决策协议

模型接收业务日期/时区、完整用户轮次、助手历史、上一轮待答问题、当前步骤、槽位状态、阻塞字段、所有字段依赖、`WORKFLOW_CONTEXT` 和候选数量。用户消息和历史都是不可信内容，不能覆盖系统指令。

输出为严格 JSON：

- `intent`: `queue` 或 `execution_request`。
- `kind`: `answer`、`question` 或 `mixed`。
- `updates`: 有证据的 typed delta；支持队列类型/日期设置、时段/场地的替换/追加/删除、重叠确认。
- `unresolved`: 有证据的歧义/无效原因；可给出受限 issue code 和累计时长。
- `reply`: 用户确实提问时结合规则回答。
- `next_field` / `next_question`: 应用更新后仍需确认时选择一个活动缺口并生成单项追问。

即时真实预约、查询、下单、付款请求必须走拒绝分支；用户表达“希望开票时自动预约/付款”属于未来队列意向。LLM 不输出隐藏推理，也不对候选做写入或执行。

## LangGraph 单轮流程

`prepare_context → interpret_turn (LLM) → apply_to_candidate_state → validate_and_reconcile → clarification / preview / escalation / unsupported → finish`

模型可在所有当前活动且依赖已满足的阻塞字段中选择优先项。队列类型、日期、时段/重叠/场地依赖由服务端强制；模型越级或选择非活动字段时，使用有效缺口回退并记录建议与最终选择。模型对“当前是否 ready”的判断不具权威性，ready 由全部槽位验证结果决定。

每轮只调用一次模型，结构化输出错误最多重试一次。Provider 错误明确返回，不当作用户输入失败。用户可修复的问题继续在下一轮处理；轮数/重复次数到限后升级到手动选择预约。

## 状态与事实来源

- 新 Agent 状态 (`agent_state` v3) 持久化规范化 `Draft`，不保存模型生成的伪自然语言，不在下一轮重新解析整段文本。
- 原始用户轮次、助手问题/答复和每轮已验证字段/原文 evidence 保存在 `response_history`，可用于对话追溯。
- 已有 v2 `normalized_turns` 仅在恢复时迁移一次；新 turn 通过 typed delta 更新事实。
- 更新先应用到状态副本，再统一验证；无效模型输出不写入对话状态。
- `business_date` 固定在会话开始时，跨午夜相对日期不漂移。
- 候选由服务器从已验证事实生成。队列保存使用现有人工队列 API 和版本 CAS；保存、排期、自动执行彼此分离。

## 评估矩阵

| 维度 | 覆盖情形 | 通过条件 |
|---|---|---|
| 上下文理解 | 单句多事实、数字/后者等短答、引用先前选项、跨轮更正、问答加事实 | 正确更新；不重复询问已确认信息 |
| 动态优先级 | 两个活动时长组都缺字段、用户当前偏好某组、低优先级字段先已给出 | 模型可选活动缺口；不越过硬依赖；trace记录最终选择 |
| 修改语义 | 替换、追加、删除、只保留、队列类型切换 | 只影响目标字段/时长组；无隐式跨组继承 |
| 歧义 | 日期/星期不明、单端时间、累计3小时、时间重叠、时段指定不同场地 | 只追问所需信息；不得猜测或预览 |
| 业务约束 | 过去日期、09:00前/22:00后、非整点、非法时长、场地0/11、超32项 | 服务端阻止预览并解释具体缺口 |
| 范围与安全 | 即时预约/付款、未来自动执行意向、提示注入、敏感字符串、非法 JSON/字段 | 即时执行拒绝；未来意向可整理；无凭据泄露或外部调用 |
| 对话与存储 | 用户问规则后保留进度、轮数上限、重放、并发写、v2迁移、历史恢复 | 状态一致；无重复写入；可恢复 |
| 结果完整性 | 候选队列、32项边界、保存版本冲突、重复请求 | 候选只由验证事实生成；重算保留已答内容；没有用户确认不保存 |

CI 使用合成模型检查 schema、结构化状态更新、硬门槛、CAS 和无副作用；真实模型矩阵单独检查自然语言理解、动态优先级、问题回答和追问。不同证据分别报告。固定脚本模型只能证明接口和验证器，不证明真实模型语义质量。

## 设计经验

- LangGraph 文档把 predetermined code paths 归为 workflow，把动态选择过程归为 agent；本功能是两者混合：模型选择对话下一步，业务依赖和真实性校验保留为硬门槛。
- 保留原始 turns 和 canonical facts；prompt 从状态动态组装。不要把结构化模型输出再编译成自然语言交给规则解析器。
- 测试按失败来源分类：模型语义、prompt/上下文、服务端硬门槛、历史迁移、Provider/网络、界面/运行版本。Provider 暂时故障不得误报成模型意图失败。
- 实时模型只用合成预约信息验证，不使用真实 Token 做上游调用，不创建队列、不预约、不付款。
