# V1 Credential and Token Lifecycle Design

- Date: 2026-10-07
- Status: Design draft / awaiting user review
- Parent architecture: [V1 Final Architecture Spec](2026-10-07-multiuser-booking-design.md)
- Predecessor milestone: V1 Identity and App Foundation, tag `v1-identity-foundation`

## 1. Purpose

Define the next independently reviewable subsystem after identity foundation: user-owned upstream Credentials and their Token lifecycle. A user must be able to add, validate, rotate, inspect safe expiry metadata for, disable, and soft-delete a Credential without exposing its Token or upstream personal data.

This design retains Flask + Vue + SQLite, server-side Sessions, strict `user_id` isolation, and the existing local-first development model. It adds no service, queue, or database server.

## 2. Scope

### Included

- Credential and append-only CredentialTokenRevision persistence and migration from schema version 1.
- Application-level authenticated encryption for Token revisions, with versioned keys and authenticated context.
- Local parsing of JWT `exp` as a reminder only; a req-confirmed read-only upstream check remains the evidence of current validity.
- Same-account Token rotation, opaque account fingerprints, safe status reporting, user-scoped APIs, and Vue management UI.
- A persistent, service-wide UpstreamRequestGate for the read-only validation call. The gate is shared across all users and Credentials and honors configured spacing and upstream `Retry-After` evidence.
- Synthetic, sanitized contract fixtures and temporary-database tests.

### Excluded

- Credential booking profiles or participant-data entry. These require a separate reviewed design because they contain personal information and are not needed to validate a Token.
- ReservationIntent, BookingPlan, BookingJob, Worker execution, execution locks, booking availability, booking/payment calls, Agent tools, LLM Provider configuration, and Tailscale deployment.
- Automatic Token refresh or upstream Token revocation.

## 3. Upstream Evidence and Contract Boundary

The local `req/` capture set contains a `POST` request to:

`/service/appointment/appointment/userAddress/getUserInfo`

The captured successful response envelope is `success`, `message`, and `resultData`; the observed success samples have `success=true` and `message=CORE10008`. The observed `resultData` contains `idserial`, `tel`, and `username`. Four captures across two known Tokens show the same `idserial`; the official frontend calls `getUserInfo()` during page loading, labels `idserial` as `证件号`, and uses `user.idserial` as `reservationPerson` in the later booking request. This is positive same-account continuity evidence and establishes that the response contains high-sensitivity identity data, but does not establish uniqueness across accounts or future stability. The four `getUserInfo` samples are successful; they do not establish the invalid-Token response mapping. No live probe is authorized by this design.

The validation adapter accepts only the exact response shape and endpoint-specific success/error combinations established from `req/` and the official frontend. HTTP 200 alone is not success. Missing/changed fields, unknown message codes, ambiguous authentication failures, or unreadable identity values fail closed. Until an explicit invalid-Token response is evidenced, non-success responses remain `validation_unknown`/contract failure and cannot set `invalid`. No endpoint other than the confirmed read-only `getUserInfo` flow is used to validate a Token in this phase.

Before implementation, Task 0 of the plan must verify from available captures and official frontend evidence: repeated same-account `idserial` consistency, any explicit account-identity semantics, possible empty/change/non-unique cases, and endpoint-specific invalid-Token response behavior. If these facts cannot be established, do not persist a usable first Credential and do not allow rotation; fail closed and return the unresolved evidence as a blocker for user review. The implementation must not fall back to a display name, telephone number, fuzzy match, or a guessed identifier. No live upstream call may be used to fill evidence gaps without separate explicit authorization.

`getUserInfo` returns personal fields. The adapter processes the response in memory, extracts only the confirmed identity field needed for account continuity, computes its keyed fingerprint, and discards the response. It must not persist or return `idserial`, telephone number, username, raw JSON, request/response bodies, or a copy of the decrypted response.

The capture data and official frontend remain local analysis sources. Raw req files, real Tokens, personal data, decrypted payloads, and real request/response bodies must never enter Git, fixtures, logs, API responses, or Agent context.

## 4. Components and Data Flow

1. **Credential API and service** authenticate the current Session, bind every query to its `user_id`, validate input, and coordinate validation and revision changes.
2. **CredentialTokenService** parses only the JWT `exp` claim, delegates read-only validation, computes account/token fingerprints, and enforces version, duplicate, and rotation rules.
3. **SecretEncryptionService** encrypts and decrypts Token ciphertext with an established authenticated-encryption implementation. It never reads upstream protocol keys as application storage keys.
4. **UpstreamContractAdapter** exposes only the validated `getUserInfo` operation in this phase. It uses a dedicated safe transport and the V1 `load_settings` path; it does not import legacy `backend/client.py` (which logs request/response bodies and snippets), `backend/flow.py` (which logs `idserial` and keeps full `user_info` in flow detail), or `backend/config.py` (`config.py` loads `.env`). All upstream access goes through the shared **UpstreamRequestGate**.
5. **SQLite** stores user-owned Credentials, immutable Token revision facts, mutable Credential validation summaries, append-only validation observations, ciphertext lifecycle metadata, and the gate's shared scheduling state. No in-memory queue is an authority.
6. **Vue Credential views** submit the Token once, then show safe status, expiry metadata, the last successful validation time, and the latest validation attempt. The browser does not persist the Token or account fingerprint.

The validation request is initiated only when a user adds a Token, rotates it, or explicitly asks to validate it. This phase does not add a background Worker. Any future preflight flow reuses the same adapter and request gate rather than creating a second validation path.

## 5. Entities and Persistence

### Credential

Credential is mutable current state and contains:

- `credential_id`, `user_id`, trimmed display `label`, `credential_version`, `enabled`, `deleted_at_utc_ms`, and UTC creation/update times.
- `current_token_revision_id` and `validation_summary_revision_id`. The validation summary must always name the current revision; pointer changes reset that summary in the same transaction.
- A versioned `upstream_account_fingerprint`, its key version, and `account_fingerprint_cleared_at_utc_ms` for the soft-delete transition. The value is an internal keyed identifier and is never returned to users or Agents.
- `last_successful_validation_at_utc_ms`, `last_confirmed_validation_state`, and `requires_revalidation`. Latest attempt details are read from append-only validation observations rather than duplicated on Credential.

`last_confirmed_validation_state` is one of `never_confirmed`, `confirmed_valid`, or `confirmed_invalid`. A transient failure never changes the last confirmed state or last successful time. `last_successful_validation_at_utc_ms` and the confirmed state always pertain to `validation_summary_revision_id`; a Token rotation atomically resets that summary to the new revision's initial successful result. `credential_version` increments on applied changes to Credential lifecycle, binding, current revision, or confirmed validation summary. It does not increment for an observation-only attempt result, so a gate-denied attempt cannot stale an in-flight validation.

Disabling a Credential sets `enabled=false`. Re-enabling sets `enabled=true` and `requires_revalidation=true`; the previous confirmed result remains historical but cannot authorize further upstream use. Only a successful `/validate` of the current revision or a successful same-account rotation that creates a newly validated current revision clears `requires_revalidation`. Soft deletion hides the row, disables all use, clears its fingerprint and all revision ciphertext, and retains a safe tombstone.

Expiry is separate from confirmed validation. `expiry_state` is projected from the current revision as `expiry_unknown`, `expiry_ok`, `expiring_soon`, or `expired`. The UI also shows the separate confirmed-validity, latest-attempt, and revalidation-required states. The future `will_expire_before_job` value is a Credential+Job projection and is not implemented before BookingJob exists.

### CredentialTokenRevision

Each Token rotation appends a semantic revision with immutable facts:

- `revision_id`, `user_id`, `credential_id`, monotonic revision number, creation time, and actor.
- Token fingerprint and Token-fingerprint key version. The fingerprint is keyed and non-reversible; it is never the Token or a plain JWT payload hash.
- `token_expires_at_utc_ms` when a valid numeric `exp` can be decoded; otherwise `NULL` with `expiry_unknown`.
- `account_fingerprint_key_version` observed during initial validation.
- `initial_validation_result` and `initial_validation_at_utc_ms`. A revision is committed only after initial validation succeeds, so these are successful immutable facts; failed candidates are not persisted.
- `secret_material_active` and `ciphertext_cleared_at_utc_ms` for the ciphertext lifecycle.

The encrypted Token envelope consists of ciphertext, nonce/tag, and `encryption_key_version`. Semantic revision fields above never change after commit. The only permitted in-place changes are authenticated envelope rewrap (ciphertext/nonce/tag and encryption key version in one transaction, with a safe audit event) and secret clearing (`secret_material_active=false`, ciphertext set to NULL, and `ciphertext_cleared_at_utc_ms`). These exceptions cannot change the Token fingerprint, exp, initial validation facts, account binding, creator, or revision number.

`account_fingerprint_key_version` on a revision records which key version was used during that revision's initial validation; it is historical metadata only. The live account fingerprint and its key-version dependency reside on Credential and may be lazily rebound after successful continuity verification.

Subsequent `/validate` operations never update a Token revision. Current validation state belongs to Credential; a `CredentialValidationObservation` records append-only attempt outcomes and whether a result was applied or stale.

### CredentialValidationObservation

This append-only, non-secret audit row contains a unique monotonic `validation_attempt_id`, `user_id`, nullable `credential_id` for rejected first-create attempts, operation kind (`create_candidate`, `validate_current`, `token_rotation_candidate`), snapshot Credential version and current-token-revision ID when present, `token_revision_id` only after an immutable revision exists, start/completion times, a safe result enum, HTTP status class, gate owner/epoch when acquired, and `apply_state` (`applied`, `candidate_rejected`, `not_dispatched`, or `stale`). The shared gate allocates the attempt ID inside the acquire transaction before deciding permit/no-permit; observations are inserted once the result is known. Latest-attempt DTOs order by this allocated ID, not response completion time, so a slower earlier request cannot overwrite a newer gate-denied attempt. `applied` means the observation matched its snapshot and is eligible for the latest-attempt DTO; it does not imply that confirmed validity changed. It contains no Token, Token/account fingerprint, `idserial`, personal profile, raw request/response, or upstream free-text message. A stale result is recorded here and returned as `validation_stale`; it never changes the Credential summary. A gate-denied request is recorded as `rate_limited/not_dispatched` without changing Credential version or confirmed state.

Key rewrap, fingerprint rebind, enable/disable, and soft-delete changes append a `CredentialLifecycleAudit` with owner, Credential/revision IDs when applicable, actor, safe operation code, old/new key-version IDs, timestamp, and outcome. It contains no raw secret, personal identity, fingerprint value, or response body. Ciphertext envelope rewrap and clearing use this audit; current validation summaries do not serve as maintenance logs.

Composite uniqueness and foreign keys bind every revision and current pointer to the same owning `user_id` and Credential. API SQL always scopes by the authenticated `user_id`; it never loads by `credential_id` alone and checks ownership later in Python.

The existing migration `0001_identity.sql` remains immutable. Credential, Token revision, validation-observation, lifecycle-audit, and shared gate tables use a new numbered migration, initially `0002_credentials.sql`, applied only by the explicit migration command. Flask startup remains read-only and fails fast on an unready schema.

## 6. Secret and Fingerprint Protection

### Token encryption

- Use AES-256-GCM through the project's existing `pycryptodome` dependency, with a fresh 96-bit nonce and 128-bit authentication tag for each encryption. Do not add another crypto service or custom cipher.
- Bind ciphertext to `user_id`, `credential_id`, `revision_id`, and key version using authenticated additional data. Moving ciphertext between rows or owners must fail authentication.
- Load an explicit versioned application keyring from protected environment/secret-manager configuration, conceptually `APP_CREDENTIAL_ENCRYPTION_KEYS` plus `APP_CREDENTIAL_ENCRYPTION_ACTIVE_KEY_ID`. The keyring maps unique key-version IDs to canonical base64url-encoded 32-byte CSPRNG keys, and the active key ID is explicit. Decryption may use retained older key versions during rotation.
- Keep the application encryption key separate from upstream AES request-encryption material, `CSRF_HMAC_SECRET`, database contents, and account-fingerprint HMAC keys. Never put any secret in SQLite, Git, logs, or `AppSettings.__repr__`.
- Key-version IDs use a strict 1–32 character ASCII allowlist. Keyring parsers reject duplicate JSON/object IDs before constructing a mapping, empty rings, missing active IDs, malformed/noncanonical base64url, decoded lengths other than 32 bytes, all-printable decoded UTF-8 strings, repeated/default placeholders, and any decoded key material reused across encryption and HMAC rings. Keys must be generated by CSPRNG; format checks are fail-fast guards, not proof of entropy. `AppSettings` stores parsed keyring bytes in `repr=False` fields. `create_app(config)` must not copy raw keyring values or active key IDs into ordinary Flask config; the current factory filters only the CSRF secret, so the Credential implementation must extend that secret-field filtering and add a regression test.
- Key bytes are immutable under a key ID; new material always receives a new key-version ID. All application processes must use the same retained key IDs and active IDs during a rollout. A request snapshots the active/retained key-version set and rechecks it before commit; keyring changes happen only through an explicit coordinated maintenance/deployment procedure, never through a user API request.
- A read-only startup key-dependency check is separate from schema migration and key rotation. Encryption keys are required only for revisions with `secret_material_active=true`; account HMAC keys are required for every non-deleted Credential still referencing that version; Token HMAC keys are required only for current revisions whose fingerprint is still used for `token_already_current`. Inert tombstones and historical fingerprints that are no longer compared do not keep keys live. A missing live dependency fails fast; it is never repaired by silently accepting a new key. Validation must distinguish a live key dependency from a historical key ID retained only as audit metadata.
- Key rewrap is available only through an explicit CLI/maintenance operation, never inline with ordinary Credential API requests. It atomically re-encrypts retained active ciphertext under the new key version, verifies authentication before commit, and retains old keys until no live ciphertext references them. A partial rewrap rolls back; key IDs never change without a successful ciphertext update.

### Account and Token fingerprints

- Load a separate versioned HMAC keyring from protected configuration, conceptually `APP_UPSTREAM_FINGERPRINT_KEYS` plus `APP_UPSTREAM_FINGERPRINT_ACTIVE_KEY_ID`. HMAC values are independent 32-byte CSPRNG secrets with strict canonical base64url decoding. Key IDs are unique, the active key must exist, and encryption/HMAC key material cannot be reused across keyrings. HMAC settings are excluded from repr and logs.
- Once Task 0 proves that `idserial` is the stable same-account field, derive the account fingerprint with HMAC-SHA-256 over its exact UTF-8 bytes, an unambiguous length prefix, and the `upstream-account-v1` domain separator. Do not trim, casefold, parse as an integer, or hash an unconfirmed field. Do not use an unkeyed hash of `idserial`.
- Derive Token fingerprints with the distinct `credential-token-v1` domain separator using the fingerprint keyring. Compare a candidate Token fingerprint only with the current revision fingerprint under that revision's key version. An exact current match returns `token_already_current`, appends no revision, and performs no upstream call; the user may separately invoke `/validate`. Historical Token reuse is not prohibited in V1 because no req evidence establishes a ban. Historical fingerprints are audit-only and do not retain an HMAC key dependency.
- Store only keyed fingerprints and key-version IDs. Do not expose values, use them as UI identifiers, or log them. A Token revision's fingerprint and fingerprint-key version are immutable. If the active Token-HMAC key changes, new revisions use the new key; an existing current revision continues to use its original key for `token_already_current` comparison. Keep that key while any current revision references it. When the Credential rotates to a different Token or is deleted, the former fingerprint becomes inert historical metadata; retire its key once no current Token fingerprint or account fingerprint requires it. Do not rewrite an immutable revision merely to rekey its fingerprint.
- Account fingerprint key rotation is lazy. On a successful `/validate` or Token rotation for a Credential on key v1 while v2 is active: compute the candidate identity HMAC with the stored v1 key; compare with the current fingerprint using `hmac.compare_digest`; only on continuity success compute the v2 HMAC and conditionally update the fingerprint/key version in the final Credential transaction. Discard raw `idserial` immediately. Keep every old account HMAC key while any non-deleted Credential, including disabled Credentials, references it. Do not batch-network all Credentials during schema migration or ordinary requests. Before future execution-lock work, all related Credentials must be preflight-rebound to the active version; lock-key migration must be atomic before retiring old keys.

## 7. Token State and Validation Rules

Expiry, confirmed upstream validity, latest validation attempt, and Credential usability are independent dimensions.

Expiry state on the current Token revision:

- `expiry_unknown`: `exp` is absent or cannot be parsed safely.
- `expiry_ok`: valid `exp` is beyond the configured reminder window.
- `expiring_soon`: valid `exp` is within the reminder window, default 7 days.
- `expired`: valid `exp` is at or before current UTC time.

Confirmed validation state on Credential:

- `never_confirmed`;
- `confirmed_valid`;
- `confirmed_invalid`.

Latest attempt result in `CredentialValidationObservation`:

- `success`;
- `explicit_invalid`;
- `network_error`;
- `rate_limited`;
- `contract_drift`;
- `validation_unknown`;
- `unresolved_identity`;
- `internal_error`.

A timeout, 429, 5xx, or contract drift updates the latest attempt result only; it never converts an earlier `confirmed_valid` into `confirmed_invalid` and never changes `last_successful_validation_at_utc_ms`. UI must show both the last successful validation time and the most recent attempt result; it must not present historical validity as permanent.

Effective usability is evaluated separately:

- `active`: user may explicitly validate or rotate the current Token.
- `disabled`: no upstream calls are allowed until the user re-enables it. Re-enabling sets `requires_revalidation=true`; historical confirmed state remains visible, but the current Token is not usable until a successful `/validate` or a successful validated Token rotation clears the flag.
- `deleted`: hidden from normal listing and barred from new use; soft deletion is not upstream Token revocation.

The UI projects a simple safe status from these dimensions in this precedence order: deleted/disabled or `requires_revalidation` is unusable; `expired` is expired; `confirmed_invalid` is invalid; `never_confirmed` or `expiry_unknown` is unknown; otherwise show `expiring_soon` or valid. A transient latest attempt failure remains a separate warning even if the last confirmed state is valid.

JWT expiry parsing rules are strict and non-authoritative:

- Token input is a non-empty UTF-8 string, at most 16 KiB, with no control characters or leading/trailing whitespace. Malformed JWT syntax may still have `expiry_unknown`; it is not by itself proof that upstream authentication is invalid.
- Parse only `exp`, using a JSON number parser that rejects `bool`, `NaN`, `Infinity`, and `-Infinity`. Accept only finite NumericDate values in the representable UTC range `0` through `253402300799.999` seconds, exactly convertible to integer milliseconds. Check decimal conversion and integer overflow before writing SQLite values.
- Any parse/type/range/overflow failure yields `expiry_unknown`; it does not mark the Token invalid. A valid `exp` at or before now blocks the validation call before network dispatch and is `expired`.
- JWT decoding does not validate its signature. Only the endpoint-specific, contract-confirmed `getUserInfo` response establishes current Token validity.

`will_expire_before_job` is calculated later per Credential+Job from that Job's current resolved execution time. It must not be stored as a global Credential state. If a submitted Token has a parseable `exp` at or before the current UTC time, reject it before the validation call. An expired/invalid Credential cannot be used to query `getUserInfo`, booking availability, prices, orders, or write endpoints; an explicit user-submitted replacement is the only path to recovery.

## 8. Operations and API Semantics

All mutation routes require a valid server Session, Origin/Referer validation, and the existing session-bound CSRF token.

- `GET /api/credentials` lists only the current user's non-deleted Credentials and safe metadata: `credential_id`, `label`, `credential_version`, `current_token_revision_id`, `enabled`, `requires_revalidation`, `expiry_state`, `last_confirmed_validation_state`, `last_successful_validation_at_utc`, and the newest validation observation's `validation_attempt_id`, `attempt_at_utc`, `operation_kind`, `current_token_revision_snapshot_id`, nullable `token_revision_id`, `attempt_result`, and `apply_state`. A null `token_revision_id` means the observation was for a candidate that never became a revision. The observation projection is append-only-derived; there are no duplicated mutable last-attempt fields on Credential. It omits Token values, raw profile data, Token fingerprints, and account fingerprints. Times use RFC 3339 UTC.
- All credential JSON bodies are capped at 64 KiB before parsing; unknown fields are rejected. `POST /api/credentials` accepts a trimmed `label`, one `token`, and optional duplicate-confirmation records `[{credential_id, credential_version}]`. Label is 1–128 Unicode code points after trim and rejects Unicode control characters. Token is a UTF-8 string with 1–16,384 encoded bytes; reject control characters and invalid surrogate sequences, preserve the exact input bytes, and never log it. It safely parses expiry and acquires the shared gate. If no permit exists, append a `rate_limited/not_dispatched` observation with no Credential ID and return immediately; do not persist the candidate Token. With a permit, validate the candidate and compute account-fingerprint candidates under every retained HMAC key before persistence. Its final `BEGIN IMMEDIATE` transaction rechecks non-deleted Credential matches for the same `user_id` across all retained key versions. It creates Credential, initial Token revision, and initial validation summary atomically only if identity and duplicate policy are satisfied. A first usable Credential is never persisted if account identity cannot be established.
- `POST /api/credentials/{credential_id}/validate` requires `expected_credential_version` and `expected_current_token_revision_id`. It snapshots the owned Credential, then acquires the gate with a short transaction that rechecks the same version, state, revision, and expiry immediately before declaring the request in flight. If no permit exists, it appends a `rate_limited/not_dispatched` observation and immediately returns 429 without changing Credential version or confirmed state. It calls the adapter without a database write lock, then reopens `BEGIN IMMEDIATE` and conditionally applies the result only if owner, non-deleted/enabled state, version, current revision, `requires_revalidation`, and account binding/key version still match. It appends a `CredentialValidationObservation`. An applied success or explicit-invalid result may update the confirmed summary and increments `credential_version`; a transient failure updates only the append-only observation. A mismatch records `apply_state=stale`, returns `409 validation_stale`, and leaves the current Credential summary unchanged. An expired revision returns `422 credential_token_expired` locally without an upstream call; a confirmed-invalid revision also requires rotation. A re-enabled Credential may validate only after the explicit enable operation sets `requires_revalidation=true`.
- `POST /api/credentials/{credential_id}/token-rotation` requires the candidate `token`, `expected_credential_version`, and `expected_current_token_revision_id`. It snapshots state, validates the candidate through the gate, compares account continuity with the stored fingerprint-key version using constant-time comparison, computes a lazy rebind under the active key, and then reopens `BEGIN IMMEDIATE` to recheck ownership, enabled/non-deleted state, row version, current revision, account binding, and all key versions. A missing gate permit returns 429 immediately and records a candidate `rate_limited/not_dispatched` observation; it does not update the current revision summary. Only if every final comparison matches does it append the new immutable revision, update the current pointer and Credential validation summary, clear `requires_revalidation`, and clear the previous revision's ciphertext in one transaction. A concurrent disable/delete/rotation makes the result stale and cannot restore state or append secret material.
- Before acquiring an upstream permit for rotation, use a short `BEGIN IMMEDIATE` to verify `expected_credential_version` and `expected_current_token_revision_id`, compute the candidate fingerprint under the current revision's key version, and compare it with `hmac.compare_digest`. If equal, return `200 token_already_current`, do not add a revision, and do not make an upstream request. The user can separately request `/validate`. V1 does not reject reuse of a non-current historical Token absent req evidence; historical Token fingerprints are audit-only and are never used to enforce a reuse ban.
- `PATCH /api/credentials/{credential_id}` requires `expected_credential_version`; it may change the safe label or enable/disable state. Disabling increments the version and blocks new calls. Re-enabling increments the version and sets `requires_revalidation=true`; it never restores effective validity from historical state. A later successful validation of the current revision or a successful validated rotation clears that flag.
- `DELETE /api/credentials/{credential_id}` requires the expected version and soft-deletes only the owned Credential. Because this phase has no Job/attempt references, the transaction sets `secret_material_active=false`, clears every revision's encrypted envelope fields (`ciphertext`, nonce, and tag; not only current), records `ciphertext_cleared_at_utc_ms`, clears the active account fingerprint and records `account_fingerprint_cleared_at_utc_ms`, and retains a no-secret tombstone. Keep key-version IDs and inert fingerprint-version metadata only as audit fields. This is logical application-level clearing only; it does not promise physical removal from SQLite WAL pages, free pages, backups, or storage media. Protect the complete database/WAL/backup as encrypted sensitive data. No per-revision DEK is added. A later Job design must add reference-aware retention before clearing ciphertext.

An optional duplicate-confirmation record is a list of `{credential_id, credential_version}` values from the prior 409 response. It records the user's explicit choice for exactly those same-user, non-deleted duplicates. The final create transaction recomputes the match set under every retained account HMAC key version and compares the complete ID/version set. Any changed or additional match returns 409; no partial credential is created. This avoids making duplicate creation an implicit or race-prone side effect.

Every Credential DTO includes `credential_version` and the current revision ID so callers can use conditional updates. `credential_version` increments on lifecycle, binding, pointer, or confirmed-summary changes; append-only observations and a gate-denied result do not increment it. Cross-user Credential IDs return the same non-disclosing 404 as a missing Credential. `401` is reserved for application Session failures; an explicitly verified upstream Token failure is `422 credential_token_invalid`, never an upstream-propagated `401` that could make the frontend clear its app Session. A locally expired Token returns `422 credential_token_expired` without a request. Other safe mappings are `400` for invalid fields, `403` for CSRF/Origin/permission, `404` for missing or cross-user IDs, `409` for stale versions/validation or duplicate-confirmation conflicts, `413` for oversized request bodies, `429` with both HTTP `Retry-After` and JSON `retry_after_seconds` when the shared gate has no permit, `502` for contract drift/unclassified upstream result, and `503` for validation not configured or unavailable. A timeout/uncertain dispatch may include `retry_after_seconds` for the retained lease. Transient upstream failures never set `confirmed_invalid`.

The canonical `CredentialDTO` fields are `credential_id`, `label`, `credential_version`, `current_token_revision_id`, `enabled`, `requires_revalidation`, `expiry_state`, `token_expires_at_utc`, `last_confirmed_validation_state`, `last_successful_validation_at_utc`, and `latest_validation_attempt: {validation_attempt_id, operation_kind, current_token_revision_snapshot_id, token_revision_id, attempt_at_utc, attempt_result, apply_state}`. The latest attempt is projected from `CredentialValidationObservation`; no raw upstream status text appears in the DTO. All times are RFC 3339 UTC. Successful creation/rotation/validate responses return this safe DTO; safe error responses carry only a result code and optional retry metadata. No response includes a Token, fingerprint, or upstream identity value.

The safe operation result codes are `token_already_current` (200), `validation_stale`, `credential_duplicate_confirmation_required`, `credential_version_conflict`, and `credential_account_mismatch` (409), `credential_token_expired` (422), `credential_token_invalid` (422 only after Task 0 confirms its exact upstream mapping), `validation_rate_limited` (429 plus `retry_after_seconds`), `upstream_contract_drift` or `validation_unknown` (502), and `validation_not_configured` or `upstream_validation_unavailable` (503). Bad label/token input returns 400. CSRF/origin failures remain 403. No response propagates upstream free-text or an upstream 401 status.

Duplicate policy follows the parent architecture. A same-user, same-account non-deleted Credential, including a disabled one, produces `409 credential_duplicate_confirmation_required` with only that user's duplicate IDs, labels, enabled state, and versions. The UI recommends re-enabling the existing Credential or rotating it. The user may explicitly confirm creating a duplicate by resubmitting the candidate with the exact duplicate IDs and versions they reviewed. The final create transaction recomputes the same-user non-deleted match set under all retained HMAC key versions and permits a duplicate only if the confirmation set and versions still match. Concurrent creates therefore cannot silently create duplicates. A truly soft-deleted Credential is not a duplicate; this design permits creating a new Credential after soft deletion and does not ban historical Token reuse. Fingerprints belonging to other users are never queried for product/API disclosure; future account-level locks remain service-only.

Because user-confirmed duplicates are a V1 behavior, SQLite must not impose a UNIQUE constraint on `(user_id, fingerprint_key_version, upstream_account_fingerprint)`. The final serialized transaction and explicit confirmation set/version check are the duplicate guard. Cross-user uniqueness is also forbidden.

Validation attempts on an existing Credential update the mutable summary only when the snapshot recheck succeeds. An explicit verified invalid response changes `last_confirmed_validation_state` to `confirmed_invalid`; network error, rate limiting, contract drift, unresolved identity, or internal failure updates only latest attempt fields and preserves the confirmed state and last-success time. A rotation candidate failure is recorded as an observation and never overwrites the still-current revision's summary. Observation rows contain safe result enums only, never raw upstream messages or bodies.

The same-user duplicate rule does not use a database UNIQUE constraint on account fingerprint because V1 permits an explicit user-confirmed duplicate. The final `BEGIN IMMEDIATE` transaction serializes create attempts and compares candidate fingerprints against every retained key version for all same-user non-deleted Credentials; a same-account match requires an exact, versioned confirmation, while a changed match set returns 409. Cross-user fingerprints are not queried by this product flow and can never affect an API result.

## 9. Shared Request Gate and Failure Behavior

### Safe transport

`UpstreamContractAdapter` uses one fixed, code/config-allow-listed HTTPS origin and the confirmed `getUserInfo` path. The `req/` evidence for this endpoint is POST JSON `{}` with the upstream `token` header and direct JSON response; it does not use the other endpoints' encrypted `item` envelope or response decryption. Require the configured origin to match the evidence task's exact host; never accept a user-supplied URL. Send with `allow_redirects=false`; any 3xx is a contract/transport failure and the `token` header is never forwarded to another host. Do not reuse legacy `backend/client.py`, which logs request/response bodies and snippets and does not disable the HTTP library's default redirect behavior. TLS verification remains enabled.

Require explicit `UPSTREAM_CONNECT_TIMEOUT_SECONDS`, `UPSTREAM_READ_TIMEOUT_SECONDS`, `UPSTREAM_TOTAL_DEADLINE_SECONDS`, and `UPSTREAM_MAX_RESPONSE_BYTES`. The real monotonic wall-clock deadline covers connect, TLS, headers, and streamed body; response reading checks the deadline and byte cap and closes/cancels the connection at expiry. Connect/read timeouts alone do not satisfy the total-deadline requirement. A transport that cannot cancel a blocking read at the deadline cannot satisfy this design. Stream the body with a strict byte counter and stop at the configured cap. Oversized bodies, redirects, TLS errors, and deadline expiry fail closed without logging body, headers, Token, or personal fields.

### Persistent shared gate

Every `getUserInfo` call passes through one SQLite-backed `UpstreamRequestGate` shared across users and Credentials. The endpoint row contains `endpoint_key`, opaque per-request `lease_owner_id` (not a user ID or Token), monotonically increasing `lease_epoch`, `lease_expires_at_utc_ms`, `next_validation_attempt_id`, `active_validation_attempt_id`, active request context (`user_id`, optional `credential_id`, operation kind, snapshot Credential version/current revision), `next_allowed_at_utc_ms`, and upstream backoff state. The context contains only internal IDs and safe version metadata, never Token, fingerprint, or personal fields, and is not exposed through user APIs. Acquire/attempt-sequence allocation and gate state changes use short `BEGIN IMMEDIATE` transactions; they never hold a DB write lock across HTTP. A permit stores its allocated attempt ID in the lease so completion records the original request order. A denied permit also allocates and observes an attempt ID without creating an active lease.

Acquire atomically allocates an attempt sequence and checks the current endpoint permit, in-flight lease, configured minimum interval, and backoff. If no permit is available, the synchronous Flask request immediately appends a `rate_limited/not_dispatched` observation and returns `429 validation_rate_limited` with HTTP `Retry-After` and JSON `retry_after_seconds`; it does not sleep and does not create a hidden background queue. A complete HTTP response releases a lease only when owner ID and epoch match. `next_allowed_at_utc_ms` and Retry-After use a monotonic maximum rule so later concurrent updates cannot shorten a backoff.

Set lease expiry to request start plus the configured total deadline and explicit safety margin. Once the permit crosses the dispatch boundary, any timeout, cancellation, or incomplete response is uncertain: record `network_error`, return promptly with a retry delay, and keep the endpoint lease/backoff unavailable until the lease expiry. Do not release early just because the local caller stopped waiting. Expiry does not prove that a remote server stopped processing. If a new caller finds an expired lease, its reclaim transaction first appends a safe `network_error/stale` observation for the stored active attempt context if one does not already exist, then advances the lease epoch and may acquire a new permit if `next_allowed_at_utc_ms` also allows it. The client closes/aborts on its total deadline. Because `getUserInfo` is read-only, a late response is ignored and can never write Credential state; no side effect is replayed. Any result carrying an old owner/epoch, or arriving after lease expiry even before a new owner appears, is stale and cannot release or update a newer lease. This bounds local overlap without claiming that a lease expiry cancels remote processing.

The parent architecture records an observed successful same-endpoint interval of approximately 668 ms with no observed 429/Retry-After response, but it does not identify that endpoint as `getUserInfo`. Do not apply 668 ms here unless Task 0 proves the endpoint match. `getUserInfo` validation stays disabled until the endpoint-scoped `UPSTREAM_GET_USER_INFO_MIN_INTERVAL_MS` is explicitly configured from evidence. While disabled, add/rotate/validate return safe `503 validation_not_configured` and persist no submitted Token. Any upstream Retry-After establishes a stronger cross-Credential backoff. No per-user, per-Credential, or per-Agent permit can be combined to evade the service limit.

### Snapshot, network, and conditional write

Every validation and rotation follows the same sequence:

1. Read a user-scoped snapshot containing `credential_id`, `user_id`, `credential_version`, `current_token_revision_id`, enabled/deleted state, `requires_revalidation`, account fingerprint and key version, and the active/retained key-version set (keyring epoch). Rotation also captures expected current revision and candidate Token metadata. Do not hold a SQLite write transaction during network I/O.
2. Acquire the shared gate in a short transaction and recheck ownership, expected version/revision, enabled/non-deleted state, expiry, and configured key versions immediately before defining the request in flight. Committing the permit is the dispatch boundary. If the check fails or no gate permit exists, return without dispatching.
3. Make the bounded read-only request outside the transaction.
4. Reopen `BEGIN IMMEDIATE`. Compare every snapshot field again, including owner, row version, current revision, state, account binding/version, keyring epoch/active key IDs, and gate owner/epoch. For first creation or rotation, recheck that a parseable candidate `exp` is still in the future at commit time. Only a matching snapshot with a non-expired candidate may update Credential summary, lazy-rebind fingerprint, create/rotate a Credential, or clear `requires_revalidation`.
5. For a complete response, in the same final SQLite transaction append the safe validation observation, apply only the allowed Credential summary changes, update gate backoff monotonically, and release the permit only when owner/epoch match and the lease is still live. This makes applied state, observation, and lease release atomic. If the Credential snapshot is stale, record `apply_state=stale`, return `409 validation_stale`, and leave current state untouched. If the lease owner/epoch is stale or expired, never release or alter the newer lease; append a stale observation only if that attempt ID has not already been recorded during lease reclaim. A response that arrives after disable/delete/rotation cannot restore state or append ciphertext. A disable/delete committed after the dispatch boundary cannot recall the already-authorized in-flight read-only call; its result is stale and no subsequent call is allowed. The design does not claim a sent request can be recalled.

Candidate account HMACs are computed in memory under every retained account-fingerprint key version before the final create/duplicate transaction. The transaction queries all same-user non-deleted Credentials, including disabled ones, and compares only matching key versions. Lazy rebind first compares the new identity under the Credential's stored key using `hmac.compare_digest`; only on a match does it compute the active-key fingerprint and conditionally update. No raw identity value survives the request.

Failure rules:

- Validation occurs before a new Credential/Token revision becomes current. Timeout, 429, 5xx, malformed response, contract drift, or unresolved identity cannot change the current Credential summary or current revision pointer.
- Only an explicit invalid-Token response whose mapping is confirmed by `req` may set `confirmed_invalid`. The current four captured `getUserInfo` samples are all successful; until invalid semantics are evidenced, non-success responses remain `validation_unknown` or contract drift, not invalid.
- If account continuity cannot be proven, do not create a usable Credential, replace a Token, or guess using username/telephone similarity.
- If encryption/decryption fails, do not call upstream or return ciphertext details; fail closed with a safe operator code.
- The gate does not retry automatically or wait in the Flask request. The user may explicitly retry after the returned gate delay. Multiple Tokens cannot bypass the gate.

## 10. UI and Privacy

The Credential page shows label, `credential_version`, enabled/revalidation-required state, separate expiry and confirmed-validation states, `last_successful_validation_at_utc`, and the latest attempt time/result. It labels whether the observation is a current-Token check, a create candidate, a rotation candidate, or a request deferred by the gate. A failed rotation candidate does not make the still-current Token invalid. A prior `confirmed_valid` with a later current-Token network/429/contract failure is shown as “last confirmed valid at …; latest validation attempt failed …”, never as permanently valid. The logged-in home shell summarizes only the user's own Token expiry and validation risks. The UI provides add, validate, same-account rotate, enable/disable, soft-delete, and explicit duplicate-confirmation actions.

Token input exists only in the form's memory and an API request body. It may remain in component memory while an explicit same-user duplicate-confirmation dialog is open; clear it on final success, final failure, cancellation, or navigation. Local development uses the loopback Vite `/api` proxy; deployed browser/API traffic is same-origin HTTPS. The current CORS allowlist need not add PATCH/DELETE while this same-origin constraint holds. Any future cross-origin browser deployment must extend `security.py` preflight methods and add tests before enabling it. Never put the Token in a URL, router state, local/session storage, analytics, frontend error message, or browser log. Do not return it in API responses. The UI never displays the account fingerprint or upstream `idserial`, telephone number, or username learned during validation.

The existing HTTP helper clears in-memory application Session state on protected-route 401. Therefore upstream Token invalidity must be mapped to a non-401 safe code (`422 credential_token_invalid` only after its exact response mapping is evidenced); upstream timeouts, contract drift, 429, and 5xx use non-401 codes. Frontend state tests must prove that these upstream errors preserve the application Session, while actual Session-invalid 401 continues to clear it.

Logs use field allow-lists. They may include credential ID, revision number, endpoint identifier, HTTP status class, safe validation code, duration bucket, and request-gate outcome. They must omit Token, JWT/payload, authorization headers, raw request/response, `idserial`, phone, username, fingerprint, and URL query parameters.

## 11. Acceptance Criteria

- A new migration adds Credential, immutable Token revision facts, append-only validation/audit observations, and endpoint gate tables with user-bound foreign keys, monotonic revision numbers, non-unique account fingerprints where duplicates are allowed, and required indexes. Identity rows remain intact; readiness and checksum checks continue to work.
- Keyring startup tests reject empty rings, duplicate key IDs, a missing active key, noncanonical/malformed base64url, decoded keys not exactly 32 bytes, cross-ring key reuse, and missing keys still referenced by live rows. `create_app(config)` never copies raw keyring values into ordinary Flask config, repr, or logs. Inert tombstones/historical fingerprints that are not compared do not require retired keys.
- A valid synthetic Token can be validated by a synthetic adapter fixture; only authenticated ciphertext and safe metadata persist. Tests/logs/API/frontend state contain no Token, JWT payload, `idserial`, phone, username, fingerprint, or raw response.
- `exp` tests reject bool, NaN/Infinity, unsafe types, range overflow, and non-millisecond-exact numeric values; these become `expiry_unknown` except a valid expired NumericDate, which is blocked before network dispatch. Input tests cover empty/control/overlength Token and invalid label boundaries.
- The adapter contract test asserts POST JSON `{}`, exact allow-listed HTTPS origin/path, `token` header, direct JSON response, `allow_redirects=false`, and no item encryption/decryption for `getUserInfo`. It validates HTTP status plus endpoint-specific JSON success/message/resultData. Unknown response shapes fail closed.
- Task 0 documents pass/fail evidence for same-account `idserial` consistency/uniqueness/stability, empty/change/non-unique cases, endpoint invalid-Token mapping, and minimum request interval. If identity continuity cannot be established, no usable Credential is persisted and rotation stays blocked. No live upstream call is made in automated tests or without separate authorization.
- Repeated `/validate` calls do not mutate semantic Token revision fields. A transient timeout/429/5xx/contract drift updates the latest attempt only, preserves previous confirmed validity and last success, and the UI displays both timestamps/results.
- Validate and rotate race tests force concurrent version/current-revision changes, disable, delete, re-enable, and fingerprint-key changes between request snapshot and response. Stale results cannot overwrite current state, append a revision, restore enablement, or clear `requires_revalidation`; candidate `exp` is rechecked in the final transaction.
- Rotation with a different account or unresolved identity leaves the prior current revision untouched. A same-account rotation appends one semantic revision and atomically advances pointer/summary. A candidate matching the current Token returns `token_already_current` without a request or new revision. Historical Token reuse is not rejected in V1 absent protocol evidence.
- A disabled Credential participates in same-user duplicate detection. Default duplicate creation returns a safe same-user conflict; explicit confirmation contains exact duplicate IDs/versions. Two concurrent unconfirmed creates cannot both succeed; one creates and the other receives 409. An explicit duplicate confirmation can add one record only while the final same-user duplicate set/versions still match; a racing create that changes that set receives 409. Cross-user matches never alter API responses or logs; no global unique constraint leaks them.
- Fingerprint rebind tests cover v1 Credential with active v2, successful old-key continuity then atomic v2 rebind, mismatch rollback, and retention of v1 while any non-deleted Credential references it. Candidate duplicate checks consider all retained key versions. HMAC-key removal is rejected while referenced; inert tombstone metadata alone does not keep keys live.
- Re-enabling a disabled Credential sets `requires_revalidation`; old successful history cannot authorize calls. Only a successful current-revision validation or validated same-account rotation clears the flag. Deletion clears every revision ciphertext/nonce/tag and account fingerprint in active rows and records safe clear metadata; tests do not claim physical SQLite/WAL/backup erasure.
- Gate tests verify total monotonic deadline (not only connect/read timeout), maximum response bytes, TLS verification, redirect rejection, cross-Credential `Retry-After`, immediate 429 plus safe retry delay when no permit exists, no Flask sleep/hidden queue, matching-owner-and-epoch release, stale-owner fencing, monotonic backoff, uncertain timeout retaining its lease with a 503 retry delay, and crash recovery only after lease deadline plus safety margin.
- Attempt-order tests verify the gate allocates `validation_attempt_id` before permit/no-permit resolution; a later gate-denied observation stays the latest attempt even if a slower earlier read-only response completes afterward. Gate-denied observations do not mutate Credential version/confirmed state. Lease-reclaim tests append a safe stale observation; a late old owner cannot release a newer lease or overwrite that observation.
- Frontend tests prove upstream Token invalidity uses a non-401 code and does not clear the application Session, while Session-invalid 401 still does; same-origin Vite proxy supports PATCH/DELETE without changing the current CORS allowlist. Cross-origin use is not enabled until preflight methods are explicitly reviewed and tested.
- Cross-user Credential IDs return the same non-disclosing 404 as missing IDs. All Credential API SQL binds current `user_id`. Tests use temporary SQLite and synthetic fixtures only; they do not load `.env`, read raw req files, print secrets, or call real upstream services.
- Tailscale, BookingPlan, BookingJob, Worker, Agent, payment, booking UI, and real booking/payment requests are not added in this phase.

## 12. Handoff to Implementation Planning

After this design is approved, the separate implementation plan should preserve Task-sized, test-first commits on a short-lived feature branch/worktree based on `main`, with final rebase, full backend/frontend/build acceptance, fast-forward merge, cleanup, and a milestone tag. Task 0 must be read-only: inspect only local req captures and official frontend source in memory, extract allow-listed method/path/header/body-key and response-shape evidence, and never output raw values. It must attempt to establish same-account `idserial` stability/uniqueness, empty/change/non-unique behavior, invalid-Token response mapping, and endpoint-specific timing evidence. Passing requires enough positive evidence to bind Credential rotations to the same account and classify the getUserInfo success response. If those facts cannot be established, the plan pauses before enabling any live validation call and returns the unresolved question for user review; it must not use a guessed identity field or invent a timing interval. No live call is permitted by Task 0.

Approval of this design permits drafting that implementation plan only. It does not authorize beginning Credential code, live upstream validation, BookingJob work, or deployment.
