# V1 Credential and Token Lifecycle Design

- Date: 2026-10-07
- Status: Design draft / awaiting user review
- Parent architecture: [V1 Final Architecture Spec](2026-10-07-multiuser-booking-design.md)
- Predecessor milestone: V1 Identity and App Foundation, tag `v1-identity-foundation`

## 1. Purpose

Define the next independently reviewable subsystem after identity foundation: user-owned upstream Credentials and their Token lifecycle. A user must be able to add, validate, rotate, inspect safe expiry metadata for, disable, and soft-delete a Credential without exposing its Token or upstream personal data.

This design retains Flask + Vue + SQLite, server-side Sessions, strict `user_id` isolation, and the existing local-first development model. It adds no service, queue, or database server.

## 2. Scope

### Included

- Credential and append-only CredentialTokenRevision persistence and migration from schema version 1.
- Application-level authenticated encryption for Token revisions, with versioned keys and authenticated context.
- Local parsing of JWT `exp` as a reminder only; a req-confirmed read-only upstream check remains the evidence of current validity.
- Token rotation only for `confirmed` account bindings, same-user confirmed-account duplicate prevention, opaque account/Token fingerprints, safe status reporting, user-scoped APIs, and Vue management UI.
- A persistent, service-wide UpstreamRequestGate for the read-only validation call. The gate is shared across all users and Credentials and honors configured spacing and upstream `Retry-After` evidence.
- Synthetic, sanitized contract fixtures and temporary-database tests.

### Excluded

- Credential booking profiles or participant-data entry. These require a separate reviewed design because they contain personal information and are not needed to validate a Token.
- ReservationIntent, BookingPlan, BookingJob, Worker execution, execution locks, booking availability, booking/payment calls, Agent tools, LLM Provider configuration, and Tailscale deployment.
- Automatic Token refresh or upstream Token revocation.

## 3. Upstream Evidence and Contract Boundary

The local `req/` capture set contains a `POST` request to:

`/service/appointment/appointment/userAddress/getUserInfo`

The captured successful response envelope is `success`, `message`, and `resultData`; the observed success samples have `success=true` and `message=CORE10008`. The observed `resultData` contains `idserial`, `tel`, and `username`. Four captures across two known Tokens show the same `idserial`; the official frontend calls `getUserInfo()` during page loading, labels `idserial` as `证件号`, and uses `user.idserial` as `reservationPerson` in the later booking request. This is positive continuity evidence within the observed sample and confirms that the response contains high-sensitivity identity data. It does not prove that `idserial` is globally unique across upstream accounts or permanently stable for every account. The four `getUserInfo` samples are successful; they do not establish the invalid-Token response mapping. No live probe is authorized by this design.

The validation adapter accepts only the exact response envelope and endpoint-specific success/error combinations established from `req/` and the official frontend. HTTP 200 alone is not success. Missing/changed envelope fields or unknown message codes fail closed. A personal account-identity field is required only for account-continuity operations; if it is unavailable while the confirmed Token-success envelope remains intact, the Token may still validate and the Credential remains or becomes `unresolved` without storing an account fingerprint. For an existing `confirmed` binding, a missing identity field is not by itself proof of a different account and does not overwrite or downgrade the binding; it is reported as an unresolved account-binding outcome. Until an explicit invalid-Token response is evidenced, non-success responses remain `validation_unknown`/contract failure and cannot set `invalid`. No endpoint other than the confirmed read-only `getUserInfo` flow is used to validate a Token in this phase.

Task 0 records two independent evidence capabilities; it does not require finite captures to prove mathematical global uniqueness or permanent future stability:

1. **`token_validation_capability`** is supported when local `req/` and official frontend evidence establish the exact `getUserInfo` method/path/header/body, a known successful HTTP and JSON envelope including the confirmed `success=true` plus `message`/`resultData` combination, and at least one recorded successful call for a known Token. The implementation must discard sensitive response fields after in-memory processing and keep them out of persistence, logs, API responses, and Agent context. This capability allows safe read-only Token validation and creation of a Credential whose Token is confirmed valid. If the second capability is not supported, that Credential starts with `account_binding_state=unresolved`.
2. **`account_continuity_capability`** is supported only when the observed `req/` and official frontend evidence is sufficient to treat an allow-listed identity field as a continuity signal when replacing a Token. Task 0 records the observed sample range, field shape/semantics, repeated same-account observations, and what remains unproven. It need not prove global uniqueness or future permanence. If evidence is insufficient, account binding remains unresolved; Task 0 still passes for Token validation when the first capability is supported.

The two capabilities are independent. A successful token-validation capability is not blocked merely because account continuity remains unresolved. An unresolved Credential may be validated again, disabled, or deleted, but cannot be rotated, included in same-account duplicate matching, or used by future work that requires an account identity or `UpstreamAccountExecutionLock`. Only a later successful read-only validation under a currently approved identity contract can promote it to `confirmed`. Never fall back to username, telephone number, display name, user-provided confirmation, or fuzzy matching. Unknown invalid-Token semantics remain unresolved and cannot be inferred from HTTP status alone. No live upstream call may be used to fill evidence gaps without separate explicit authorization.

`getUserInfo` returns personal fields. When account-continuity evidence is approved, the adapter processes the allow-listed identity field in memory, computes its keyed fingerprint, and discards the response. In token-validation-only mode it discards all personal result fields without deriving or persisting an account identity. Neither path may persist or return `idserial`, telephone number, username, raw JSON, request/response bodies, or a copy of the decrypted response.

The capture data and official frontend remain local analysis sources. Raw req files, real Tokens, personal data, decrypted payloads, and real request/response bodies must never enter Git, fixtures, logs, API responses, or Agent context.

## 4. Components and Data Flow

1. **Credential API and service** authenticate the current Session, bind every query to its `user_id`, validate input, and coordinate validation and revision changes.
2. **CredentialTokenService** parses only the JWT `exp` claim, delegates read-only validation, maintains the three-state account binding, computes account/Token fingerprints when their evidence capability is available, and enforces version, same-user uniqueness, and rotation rules.
3. **SecretEncryptionService** encrypts and decrypts Token ciphertext with an established authenticated-encryption implementation. It never reads upstream protocol keys as application storage keys.
4. **UpstreamContractAdapter** exposes only the validated `getUserInfo` operation in this phase. It uses a dedicated safe transport and the V1 `load_settings` path; it does not import legacy `backend/client.py` (which logs request/response bodies and snippets), `backend/flow.py` (which logs `idserial` and keeps full `user_info` in flow detail), or `backend/config.py` (`config.py` loads `.env`). All upstream access goes through the shared **UpstreamRequestGate**.
5. **SQLite** stores user-owned Credentials, immutable Token revision facts, mutable Credential validation summaries, append-only validation observations, ciphertext lifecycle metadata, and the gate's shared scheduling state. No in-memory queue is an authority.
6. **Vue Credential views** submit the Token once, then show safe status, expiry metadata, the last successful validation time, and the latest validation attempt. The browser does not persist the Token or account fingerprint.

The validation request is initiated only when a user adds a Token, rotates it, or explicitly asks to validate it. This phase does not add a background Worker. Any future preflight flow reuses the same adapter and request gate rather than creating a second validation path.

## 5. Entities and Persistence

### Credential

Credential is mutable current state and contains:

- `credential_id`, `user_id`, trimmed display `label`, `credential_version`, `enabled`, `deleted_at_utc_ms`, and UTC creation/update times.
- `current_token_revision_id` and `account_binding_state` (`unresolved`, `confirmed`, or `needs_reconfirmation`). The latter is independent of enabled state and `requires_revalidation`.
- A nullable versioned `upstream_account_fingerprint`, its fingerprint key version, `account_identity_contract_version`, and `account_fingerprint_cleared_at_utc_ms` for the soft-delete transition. A live `unresolved` Credential has no fingerprint or identity-contract version; a live `confirmed` Credential has both; `needs_reconfirmation` retains both only for a future continuity check and cannot participate in duplicate matching or execution locks. Soft deletion clears the fingerprint/key/contract version and sets the tombstone's binding state to `unresolved`, so deleted rows have no active account binding. The fingerprint is never returned to users or Agents.
- `last_successful_validation_at_utc_ms`, `last_confirmed_validation_state`, and `requires_revalidation`. Latest attempt details are read from append-only validation observations rather than duplicated on Credential.

`last_confirmed_validation_state` is one of `never_confirmed`, `confirmed_valid`, or `confirmed_invalid`. These summary fields always describe `current_token_revision_id`; there is no second revision pointer. A transient failure never changes the last confirmed state or last successful time. Token rotation creates an immutable revision, moves `current_token_revision_id`, resets/updates the summary to the newly successful current Token, clears `requires_revalidation`, and increments `credential_version` in one transaction. `credential_version` also increments when account binding state/fingerprint/contract version or Credential lifecycle changes. It does not increment for an observation-only attempt result, so a gate-denied attempt cannot stale an in-flight validation.

Account-binding transitions are constrained as follows:

- A newly created Credential is `unresolved` when Token validation succeeds but continuity evidence is not approved. A successful read-only validation under an approved identity contract can move `unresolved → confirmed` only after it derives the fingerprint and the final transaction confirms that no same-user confirmed Credential already matches.
- `confirmed` remains confirmed through ordinary network errors, 429, 5xx, timeout, and contract drift that does not invalidate the identity contract. These failures change only the latest attempt observation.
- An Adapter/identity-contract release must explicitly classify whether each prior identity-contract version remains trusted. If it does not, affected active Credentials move to `needs_reconfirmation` before any account-bound use; this is a versioned state transition with a lifecycle audit, not a consequence inferred from a transient request failure.
- `confirmed → needs_reconfirmation` occurs only when the identity contract used to establish the binding is explicitly retired, an Adapter upgrade can no longer trust that binding, or a successful current-Token response creates a real continuity contradiction. A mismatch never overwrites the prior fingerprint. A failed candidate Token during rotation is rejected without changing the current Credential's binding.
- `needs_reconfirmation → confirmed` requires one successful read-only validation of the current Token under the currently approved identity contract and a constant-time continuity match against the retained fingerprint. A mismatch leaves the state unchanged and fails closed. If the current contract cannot produce an identity comparable to the retained fingerprint, the Credential remains `needs_reconfirmation`; the user must soft-delete it and create a new Credential under the current approved contract rather than rebind it by another field. Before promotion, the transaction also checks same-user uniqueness; an existing match returns a safe conflict and does not promote the row.
- No user confirmation, label, username, telephone number, or fuzzy match can establish or restore account binding. Disabling or enabling a Credential does not change `account_binding_state`; enabling independently sets `requires_revalidation=true`. Soft deletion records the prior enum in a safe lifecycle audit, clears the live fingerprint/key/contract version, sets the tombstone state to `unresolved`, and disables all binding use.

Disabling a Credential sets `enabled=false`. Re-enabling sets `enabled=true` and `requires_revalidation=true`; the previous confirmed result remains historical but cannot authorize further upstream use. Only a successful `/validate` of the current revision or a successful same-account rotation that creates a newly validated current revision clears `requires_revalidation`. Soft deletion hides the row, disables all use, clears its fingerprint and all revision ciphertext, and retains a safe tombstone.

Expiry is separate from confirmed validation. `expiry_state` is projected from the current revision as `expiry_unknown`, `expiry_ok`, `expiring_soon`, or `expired`. The UI also shows the separate confirmed-validity, latest-attempt, and revalidation-required states. The future `will_expire_before_job` value is a Credential+Job projection and is not implemented before BookingJob exists.

### CredentialTokenRevision

Each Token rotation appends a semantic revision with immutable facts:

- `revision_id`, `user_id`, `credential_id`, monotonic revision number, creation time, and actor.
- Token fingerprint and Token-fingerprint key version. The fingerprint is keyed and non-reversible; it is never the Token or a plain JWT payload hash.
- `token_expires_at_utc_ms` when a valid numeric `exp` can be decoded; otherwise `NULL` with `expiry_unknown`.
- Nullable `initial_account_fingerprint_key_version` and `initial_account_identity_contract_version`, populated only if initial validation established a binding; these are immutable historical facts, not pointers to the current binding. If the Credential starts unresolved and is confirmed by a later validation, the revision is not rewritten.
- `initial_validation_result` and `initial_validation_at_utc_ms`. A revision is committed only after initial validation succeeds, so these are successful immutable facts; failed candidates are not persisted.
- `secret_material_active` and `ciphertext_cleared_at_utc_ms` for the ciphertext lifecycle.

The encrypted Token envelope consists of ciphertext, nonce/tag, and `encryption_key_version`. Semantic revision fields above never change after commit. The only permitted in-place changes are authenticated envelope rewrap (ciphertext/nonce/tag and encryption key version in one transaction, with a safe audit event) and secret clearing (`secret_material_active=false`, ciphertext set to NULL, and `ciphertext_cleared_at_utc_ms`). These exceptions cannot change the Token fingerprint, exp, initial validation facts, account binding, creator, or revision number.

`initial_account_fingerprint_key_version` and `initial_account_identity_contract_version` record which identity contract/key version, if any, established a binding during that revision's initial validation; they are historical metadata only. The live account fingerprint and its key-version dependency reside on Credential and may be lazily rebound after successful continuity verification.

The Token-fingerprint key version on a non-current revision is also inert audit metadata. Only the current revision's Token fingerprint requires its key for `token_already_current` comparison; non-current fingerprints are never compared for a historical-reuse policy.

Subsequent `/validate` operations never update a Token revision. Current validation state belongs to Credential; a `CredentialValidationObservation` records append-only attempt outcomes and whether a result was applied or stale.

### CredentialValidationObservation

This append-only, non-secret audit row contains a unique monotonic `validation_attempt_id`, `user_id`, nullable `credential_id` for rejected first-create attempts, operation kind (`create_candidate`, `validate_current`, `token_rotation_candidate`), snapshot Credential version and current-token-revision ID when present, `token_revision_id` only after an immutable revision exists, `started_at_utc_ms`, `completed_at_utc_ms`, a safe Token-validation result, an optional safe account-binding outcome (`not_checked`, `unresolved`, `confirmed`, `mismatch`, or `duplicate_conflict`), HTTP status class, gate owner/epoch when acquired, and `apply_state` (`applied`, `candidate_rejected`, `not_dispatched`, or `stale`). A gate-denied attempt has start and completion times equal or immediately adjacent. The shared gate allocates the attempt ID inside the acquire transaction before deciding permit/no-permit; observations are inserted once the result is known. `latest_requested_validation_attempt` is ordered by this allocated/request ID, not completion time. It therefore means the most recently initiated attempt, not the most recently completed one; a slower earlier response cannot overwrite a newer gate-denied attempt. `applied` means the observation matched its snapshot and is eligible for this DTO; it does not imply that confirmed Token validity or account binding changed. The Credential's `last_successful_validation_at_utc_ms` independently reports the last successful Token validation. The row contains no Token, Token/account fingerprint, `idserial`, personal profile, raw request/response, or upstream free-text message. A stale result is returned as `validation_stale` and never changes the Credential summary. A gate-denied request is recorded as `rate_limited/not_dispatched` without changing Credential version or confirmed state.

Key rewrap, account-fingerprint rebind, account-binding state transitions, enable/disable, and soft-delete changes append a `CredentialLifecycleAudit` with owner, Credential/revision IDs when applicable, actor, safe operation code, old/new key-version IDs and account identity-contract versions when applicable, timestamp, and outcome. Safe binding operation codes include `binding_confirmed`, `binding_needs_reconfirmation`, `binding_reconfirmed`, and `fingerprint_rebound`. It contains no raw secret, personal identity, fingerprint value, or response body. Ciphertext envelope rewrap and clearing use this audit; current validation summaries do not serve as maintenance logs.

Composite uniqueness and foreign keys bind every revision and current pointer to the same owning `user_id` and Credential. API SQL always scopes by the authenticated `user_id`; it never loads by `credential_id` alone and checks ownership later in Python.

The existing migration `0001_identity.sql` remains immutable. Credential, Token revision, validation-observation, lifecycle-audit, and shared gate tables use a new numbered migration, initially `0002_credentials.sql`, applied only by the explicit migration command. Flask startup remains read-only and fails fast on an unready schema.

## 6. Secret and Fingerprint Protection

### Token encryption

- Use AES-256-GCM through the project's existing `pycryptodome` dependency, with a fresh 96-bit nonce and 128-bit authentication tag for each encryption. Do not add another crypto service or custom cipher.
- Bind ciphertext to `user_id`, `credential_id`, `revision_id`, and key version using authenticated additional data. Moving ciphertext between rows or owners must fail authentication.
- Load an explicit versioned application keyring from protected environment/secret-manager configuration, conceptually `APP_CREDENTIAL_ENCRYPTION_KEYS` plus `APP_CREDENTIAL_ENCRYPTION_ACTIVE_KEY_ID`. The keyring maps unique key-version IDs to canonical base64url-encoded 32-byte CSPRNG keys, and the active key ID is explicit. Decryption may use retained older key versions during rotation.
- Keep the application encryption key separate from upstream AES request-encryption material, `CSRF_HMAC_SECRET`, database contents, and the fingerprint HMAC keyring. Never put any secret in SQLite, Git, logs, or `AppSettings.__repr__`.
- Key-version IDs use a strict 1–32 character ASCII allowlist. Keyring parsers reject duplicate JSON/object IDs before constructing a mapping, empty rings, missing active IDs, malformed/noncanonical base64url, decoded lengths other than 32 bytes, and any decoded key material reused across encryption and fingerprint HMAC keyrings. Keys must be generated by CSPRNG; application format checks cannot prove actual entropy. Do not reject keys using printable-byte or vague placeholder heuristics. If a fixed development denylist is ever adopted, it must be small, explicit, and testable; V1 does not require one. `AppSettings` stores parsed keyring bytes in `repr=False` fields. `create_app(config)` must not copy raw keyring values or active key IDs into ordinary Flask config; the Credential implementation must extend secret-field filtering and add a regression test.
- Key bytes are immutable under a key ID; new material always receives a new key-version ID. All application processes must use the same retained key IDs and active IDs during a rollout. A request snapshots the active/retained key-version set and rechecks it before commit; keyring changes happen only through an explicit coordinated maintenance/deployment procedure, never through a user API request.
- A read-only startup key-dependency check is separate from schema migration and key rotation. Encryption keys are required only for revisions with `secret_material_active=true`. A fingerprint HMAC key version has an **account-fingerprint dependency** while a non-deleted Credential in `confirmed` or `needs_reconfirmation` retains a fingerprint under that version; it has a **token-fingerprint dependency** while a current Token revision's fingerprint is still used for `token_already_current`. These are dependency reasons within one fingerprint HMAC keyring, not separate keyrings. Inert tombstones and historical fingerprints that are no longer compared do not keep keys live. A missing live dependency fails fast; it is never repaired by silently accepting a new key. Validation distinguishes live dependencies from historical key IDs retained only as audit metadata.
- Key rewrap is available only through an explicit CLI/maintenance operation, never inline with ordinary Credential API requests. It atomically re-encrypts retained active ciphertext under the new key version, verifies authentication before commit, and retains old keys until no live ciphertext references them. A partial rewrap rolls back; key IDs never change without a successful ciphertext update.

### Account and Token fingerprints

- Load one versioned **fingerprint HMAC keyring** from protected configuration using `APP_UPSTREAM_FINGERPRINT_KEYS` and `APP_UPSTREAM_FINGERPRINT_ACTIVE_KEY_ID`. Keys are 32-byte CSPRNG secrets with strict canonical base64url decoding. Key IDs are unique, the active ID exists, the ring is nonempty, and fingerprint HMAC material is independent of the encryption keyring. Settings are excluded from repr and logs. Do not configure separate account and Token HMAC keyrings.
- When `account_continuity_capability` is approved, derive an account fingerprint with HMAC-SHA-256 over the allow-listed identity field's exact UTF-8 bytes, an unambiguous length prefix, and the `upstream-account-v1` domain separator. Do not trim, casefold, parse as an integer, or hash an unconfirmed field. Do not use an unkeyed hash. Persist the fingerprint only for `confirmed` or `needs_reconfirmation` state; an `unresolved` Credential has no active fingerprint.
- Derive Token fingerprints with the distinct `credential-token-v1` domain separator using the same fingerprint HMAC keyring. Compare a candidate Token fingerprint only with the current revision fingerprint under that revision's key version. An exact current match returns `token_already_current`, appends no revision, and performs no upstream call; the user may separately invoke `/validate`. Historical Token reuse is not prohibited in V1 because no req evidence establishes a ban. Historical fingerprints are audit-only and do not retain a token-fingerprint dependency.
- Store only keyed fingerprints and key-version IDs. Do not expose values, use them as UI identifiers, or log them. A Token revision's fingerprint and fingerprint-key version are immutable. If the active fingerprint HMAC key changes, new revisions use the new key; an existing current revision continues to use its original key for `token_already_current` comparison. Keep that key while any current revision references it. When the Credential rotates to a different Token or is deleted, the former Token fingerprint becomes inert historical metadata; retire its key once no current Token-fingerprint dependency or account-fingerprint dependency requires it. Do not rewrite an immutable revision merely to rekey its Token fingerprint.
- Account fingerprint key rotation is lazy and applies only while a binding can be trusted. For a `confirmed` Credential on key v1 while v2 is active, a successful current-Token validation first compares the newly derived identity under v1 with the stored fingerprint using `hmac.compare_digest`; only on continuity success does it compute the v2 fingerprint and conditionally update the fingerprint/key version in the final Credential transaction. A `needs_reconfirmation` Credential may rebind only as part of successful reconfirmation against its retained fingerprint under the currently approved identity contract. An `unresolved` Credential has no prior account fingerprint to rebind. Discard raw identity immediately. Retain every old key while any non-deleted account-fingerprint or current token-fingerprint dependency references it. Do not batch-network all Credentials during migration or ordinary requests. Before future execution-lock work, all confirmed bindings must be preflight-rebound and lock keys migrated atomically before retiring old dependencies.

## 7. Token State and Validation Rules

Expiry, confirmed upstream validity, latest validation attempt, and Credential usability are independent dimensions.

Expiry state on the current Token revision:

- `expiry_unknown`: `exp` is absent or cannot be parsed safely.
- `expiry_ok`: valid `exp` is beyond the configured reminder window.
- `expiring_soon`: valid `exp` is within the reminder window, default 7 days.
- `expired`: valid `exp` is at or before current UTC time.

Confirmed validation state on Credential:

- `never_confirmed`;
- `confirmed_valid`;
- `confirmed_invalid`.

Latest attempt result in `CredentialValidationObservation`:

- `success`;
- `explicit_invalid`;
- `network_error`;
- `rate_limited`;
- `contract_drift`;
- `validation_unknown`;
- `unresolved_identity`;
- `internal_error`.

`attempt_result` describes the Token-validation request. `account_binding_outcome` is a separate optional field with `not_checked`, `unresolved`, `confirmed`, or `mismatch`. Thus a successful Token response can leave account binding `unresolved`, or validate the Token while moving a contradictory binding to `needs_reconfirmation`. These dimensions are never collapsed into one status.

A timeout, 429, 5xx, or contract drift updates the latest attempt result only; it never converts an earlier `confirmed_valid` into `confirmed_invalid` and never changes `last_successful_validation_at_utc_ms`. UI must show both the last successful validation time and the most recent attempt result; it must not present historical validity as permanent.

Account-binding state is evaluated separately:

- `unresolved`: Token validation may be retried; the Credential may be disabled or deleted. No rotation, same-account duplicate matching, or future account-bound BookingJob/UpstreamAccountExecutionLock use is allowed.
- `confirmed`: a current approved identity contract and successful current-Token validation established a fingerprint. This state is required for rotation, same-user duplicate matching, and future account-bound execution.
- `needs_reconfirmation`: the previous fingerprint is retained only for an approved-contract continuity check. Rotation, duplicate matching, and future account-bound execution are paused. Recovery requires successful current-Token validation under the currently approved identity contract and a constant-time match to the retained fingerprint. An identity mismatch does not replace that fingerprint.

Effective usability is evaluated separately:

- `active`: user may explicitly validate the current Token; rotation is available only when `account_binding_state=confirmed`.
- `disabled`: no upstream calls are allowed until the user re-enables it. Re-enabling sets `requires_revalidation=true`; historical confirmed state remains visible, but the current Token is not usable until a successful `/validate` or a successful validated Token rotation clears the flag.
- `deleted`: hidden from normal listing and barred from new use; soft deletion is not upstream Token revocation.

`account_binding_state=unresolved` and `needs_reconfirmation` permit a safe read-only validation of the current Token when the Credential is enabled and does not require revalidation; they do not permit rotation or account-bound execution. `requires_revalidation=true` independently requires a successful current-Token validation before further use.

The UI projects safe status from these independent dimensions. Deleted/disabled or `requires_revalidation` blocks calls; `account_binding_state=unresolved` or `needs_reconfirmation` blocks account-bound use; `expired` is expired; `confirmed_invalid` is invalid; `never_confirmed` or `expiry_unknown` is unknown; otherwise show `expiring_soon` or valid. A transient latest attempt failure remains a separate warning even if the last confirmed state is valid.

JWT expiry parsing rules are strict and non-authoritative:

- Token input is a non-empty UTF-8 string, at most 16 KiB, with no control characters or leading/trailing whitespace. Malformed JWT syntax may still have `expiry_unknown`; it is not by itself proof that upstream authentication is invalid.
- Parse only `exp`, using a JSON number parser that rejects `bool`, `NaN`, `Infinity`, and `-Infinity`. Accept only finite NumericDate values in the representable UTC range `0` through `253402300799.999` seconds, exactly convertible to integer milliseconds. Check decimal conversion and integer overflow before writing SQLite values.
- Any parse/type/range/overflow failure yields `expiry_unknown`; it does not mark the Token invalid. A valid `exp` at or before now blocks the validation call before network dispatch and is `expired`.
- JWT decoding does not validate its signature. Only the endpoint-specific, contract-confirmed `getUserInfo` response establishes current Token validity.

`will_expire_before_job` is calculated later per Credential+Job from that Job's current resolved execution time. It must not be stored as a global Credential state. If a submitted Token has a parseable `exp` at or before the current UTC time, reject it before the validation call. An expired/invalid Credential cannot be used to query `getUserInfo`, booking availability, prices, orders, or write endpoints; an explicit user-submitted replacement is the only path to recovery.

## 8. Operations and API Semantics

All mutation routes require a valid server Session, Origin/Referer validation, and the existing session-bound CSRF token.

- `GET /api/credentials` lists only the current user's non-deleted Credentials and safe metadata: `credential_id`, `label`, `credential_version`, `current_token_revision_id`, `enabled`, `account_binding_state`, `requires_revalidation`, `expiry_state`, `last_confirmed_validation_state`, `last_successful_validation_at_utc`, and `latest_requested_validation_attempt` containing `validation_attempt_id`, `started_at_utc`, `completed_at_utc`, `operation_kind`, `current_token_revision_snapshot_id`, nullable `token_revision_id`, `attempt_result`, `account_binding_outcome`, and `apply_state`. A null `token_revision_id` means the observation was for a candidate that never became a revision. This is the most recently initiated attempt by allocated request order, not the most recently completed attempt. The observation projection is append-only-derived; there are no duplicated mutable last-attempt fields on Credential. It omits Token values, raw profile data, Token fingerprints, account fingerprints, and `account_identity_contract_version`. Times use RFC 3339 UTC.
- All credential JSON bodies are capped at 64 KiB before parsing; unknown fields are rejected. `POST /api/credentials` accepts only a trimmed `label` and one `token`; duplicate-confirmation fields are not part of V1. Label is 1–128 Unicode code points after trim and rejects Unicode control characters. Token is a UTF-8 string with 1–16,384 encoded bytes; reject control characters and invalid surrogate sequences, preserve the exact input bytes, and never log it. When this user already has a non-deleted `unresolved` or `needs_reconfirmation` Credential, reject another create before upstream dispatch with a safe binding-state conflict; this is a conservative creation gate, not fingerprint duplicate matching. If `account_continuity_capability` is unavailable and the user already has any non-deleted Credential, also reject before dispatch because the candidate cannot be proven distinct; while capability remains unavailable, at most one non-deleted Credential can exist for that user. Otherwise parse expiry and acquire the shared gate. If no permit exists, append a `rate_limited/not_dispatched` observation with no Credential ID and return immediately; do not persist the candidate Token. With a permit, validate the candidate. If account continuity is approved and an identity is returned, derive the candidate fingerprint in memory and, in the final `BEGIN IMMEDIATE` transaction, check same-user `confirmed` Credentials across every retained fingerprint key version. A matching enabled or disabled Credential returns `409 credential_account_already_configured`; no candidate is persisted. If no identity is returned and there are existing non-deleted Credentials that cannot safely be compared, return `409 credential_account_binding_unresolved` without persisting the candidate. If there is no other non-deleted Credential, create it with `account_binding_state=unresolved` and no account fingerprint. Create the immutable Token revision and current validation summary atomically only after the Token validation succeeds.
- `POST /api/credentials/{credential_id}/validate` requires `expected_credential_version` and `expected_current_token_revision_id`. It snapshots the owned Credential, then acquires the gate with a short transaction that rechecks the same version, state, revision, expiry, account-binding state, and identity-contract/key version immediately before declaring the request in flight. If no permit exists, it appends a `rate_limited/not_dispatched` observation and immediately returns 429 without changing Credential version or confirmed state. It calls the adapter without a database write lock, then reopens `BEGIN IMMEDIATE` and conditionally applies the result only if owner, non-deleted/enabled state, version, current revision, `requires_revalidation`, account binding, and key/contract versions still match. A successful Token response updates the current Token validation summary. If the current state is `unresolved` and the current approved contract supplies a reliable identity, promotion to `confirmed` requires a fingerprint and a same-user duplicate check in that transaction; if no identity is available, the Token result can still succeed while binding stays unresolved. If the state is `confirmed`, an available identity must match the stored fingerprint; a real mismatch moves it to `needs_reconfirmation` without replacing the fingerprint, while an unavailable identity alone does not establish a mismatch. If the state is `needs_reconfirmation`, only a match to the retained fingerprint can restore `confirmed`; a mismatch or unavailable identity leaves it paused. A duplicate match prevents promotion/recovery and returns a safe conflict. A transient failure updates only the append-only observation. Stale snapshots return `409 validation_stale` without changing current state. An expired revision returns `422 credential_token_expired` locally without an upstream call; a confirmed-invalid revision requires a separately validated replacement. A re-enabled Credential may validate only after the explicit enable operation sets `requires_revalidation=true`.
- `POST /api/credentials/{credential_id}/rotate-token` requires the candidate `token`, `expected_credential_version`, and `expected_current_token_revision_id`, and is permitted only for an enabled, non-deleted Credential with `account_binding_state=confirmed`. `unresolved` and `needs_reconfirmation` return safe conflict codes before dispatch. It snapshots state, validates the candidate through the gate, compares account continuity with the stored fingerprint-key version using constant-time comparison, computes a lazy rebind under the active key, and then reopens `BEGIN IMMEDIATE` to recheck ownership, enabled/non-deleted state, row version, current revision, confirmed binding, identity contract, and all key versions. A missing gate permit returns 429 immediately and records a candidate `rate_limited/not_dispatched` observation; it does not update the current revision summary. If Token validation succeeds but the candidate identity is unavailable or cannot be compared, reject the candidate with `409 credential_account_binding_unresolved`; do not rotate. Only if every final comparison matches does it append the new immutable revision, update the current pointer and validation summary, clear `requires_revalidation`, and update the live fingerprint/key/contract version as needed. In this Credential-only phase with no execution references, the prior revision's ciphertext may be cleared atomically. Once BookingJob/ExecutionAttempt references exist, retain prior ciphertext while an active attempt or unresolved side effect needs it, and clear it only after those references end. A rotation candidate that identifies another account is rejected and does not change the current Credential binding. A concurrent disable/delete/rotation makes the result stale and cannot restore state or append secret material.
- Before acquiring an upstream permit for rotation, use a short `BEGIN IMMEDIATE` to verify the expected version/revision and `account_binding_state=confirmed`, compute the candidate Token fingerprint under the current revision's key version, and compare it with `hmac.compare_digest`. If equal, return `200 token_already_current`, do not add a revision, and do not make an upstream request. The user can separately request `/validate`. V1 does not reject reuse of a non-current historical Token absent req evidence; historical Token fingerprints are audit-only and are never used to enforce a reuse ban.
- `PATCH /api/credentials/{credential_id}` requires `expected_credential_version`; it may change the safe label or enable/disable state. Disabling increments the version and blocks new calls. Re-enabling increments the version and sets `requires_revalidation=true`; it never restores effective validity from historical state. A later successful validation of the current revision or a successful validated rotation clears that flag.
- `DELETE /api/credentials/{credential_id}` requires the expected version and soft-deletes only the owned Credential. This Credential-only phase has no Job/attempt references, so its transaction sets `secret_material_active=false`, clears every revision's encrypted envelope fields (`ciphertext`, nonce, and tag), records `ciphertext_cleared_at_utc_ms`, clears the active account fingerprint/key/contract version, records `account_fingerprint_cleared_at_utc_ms`, sets the tombstone binding state to `unresolved`, and retains a no-secret tombstone. When booking execution references are introduced, soft deletion must still bar new use but retain ciphertext for active attempts/unresolved side effects until their references end, then clear it. Keep key-version IDs and inert fingerprint-version metadata only as audit fields. This is logical application-level clearing only; it does not promise physical removal from SQLite WAL pages, free pages, backups, or storage media. Protect the complete database/WAL/backup as encrypted sensitive data. No per-revision DEK is added.

There is no duplicate-confirmation record or user override. A same-user, same-account match always blocks creation; the response recommends re-enabling or rotating the existing Credential. A token-valid but continuity-unresolved candidate may be created as `unresolved` only when the user has no other non-deleted Credential, because it cannot safely be matched to an account. Until it becomes `confirmed` or is soft-deleted, another Credential cannot be created. If the unresolved row is later promoted, the final transaction performs the uniqueness check and leaves it unresolved if a confirmed match already exists.

Every Credential DTO includes `credential_version` and the current revision ID so callers can use conditional updates. `credential_version` increments on lifecycle, binding, pointer, or confirmed-summary changes; append-only observations and a gate-denied result do not increment it. Cross-user Credential IDs return the same non-disclosing 404 as a missing Credential. `401` is reserved for application Session failures; an explicitly verified upstream Token failure is `422 credential_token_invalid`, never an upstream-propagated `401` that could make the frontend clear its app Session. A locally expired Token returns `422 credential_token_expired` without a request. Other safe mappings are `400` for invalid fields, `403` for CSRF/Origin/permission, `404` for missing or cross-user IDs, `409` for stale versions/validation, `credential_account_already_configured`, unresolved/reconfirmation rotation attempts, or account-binding promotion conflicts, `413` for oversized request bodies, `429` with both HTTP `Retry-After` and JSON `retry_after_seconds` when the shared gate has no permit, `502` for contract drift/unclassified upstream result, and `503` for validation not configured or unavailable. A timeout/uncertain dispatch may include `retry_after_seconds` for the retained lease. Transient upstream failures never set `confirmed_invalid` or change account binding.

The canonical `CredentialDTO` fields are `credential_id`, `label`, `credential_version`, `current_token_revision_id`, `enabled`, `account_binding_state`, `requires_revalidation`, `expiry_state`, `token_expires_at_utc`, `last_confirmed_validation_state`, `last_successful_validation_at_utc`, and `latest_requested_validation_attempt: {validation_attempt_id, operation_kind, current_token_revision_snapshot_id, token_revision_id, started_at_utc, completed_at_utc, attempt_result, account_binding_outcome, apply_state}`. The latest requested attempt is projected from `CredentialValidationObservation` by allocated request order, not completion time; the last successful validation time remains a separate summary. No raw upstream status text appears in the DTO. All times are RFC 3339 UTC. Successful creation/rotation/validate responses return this safe DTO; safe error responses carry only a result code, optional same-user safe conflict metadata, and retry metadata. No response includes a Token, fingerprint, identity-contract version, or upstream identity value.

The safe operation result codes are `token_already_current` (200), `validation_stale`, `credential_account_already_configured`, `credential_account_binding_unresolved`, `credential_account_reconfirmation_required`, `credential_account_mismatch`, and `credential_version_conflict` (409), `credential_token_expired` (422), `credential_token_invalid` (422 only after Task 0 confirms its exact upstream mapping), `validation_rate_limited` (429 plus `retry_after_seconds`), `upstream_contract_drift` or `validation_unknown` (502), and `validation_not_configured` or `upstream_validation_unavailable` (503). Bad label/token input returns 400. CSRF/origin failures remain 403. No response propagates upstream free-text or an upstream 401 status.

The V1 same-user account rule is at most one non-deleted Credential per confirmed upstream account. Among `confirmed` bindings, the final `BEGIN IMMEDIATE` transaction compares a candidate's account fingerprint against same-user confirmed Credentials using each row's retained fingerprint-key version; the serialized check prevents concurrent create or promotion races without duplicate-confirmation sets or version-set handshakes. A disabled matching Credential still blocks creation and can be re-enabled or rotated. `unresolved` and `needs_reconfirmation` rows are deliberately excluded from fingerprint duplicate matching. To preserve the at-most-one rule without matching those states, a user may not create another Credential while an unmatchable non-deleted binding exists; when continuity capability is unavailable, a user with any non-deleted Credential may not add a second. A candidate with no returned identity also cannot be persisted beside confirmed Credentials. If later promotion/reconfirmation discovers a confirmed match, promotion is rejected and the original row remains in its prior binding state. A truly soft-deleted Credential does not block a new one. There is no cross-user uniqueness constraint or lookup for product/API disclosure; different application users may bind the same upstream account, and their only shared account identity behavior remains the future service-level execution lock.

Validation of the current Token may update Token validity and `last_successful_validation_at_utc_ms` even when account promotion is blocked; the observation reports the separate binding outcome. A current-token identity mismatch on a `confirmed` Credential changes its binding to `needs_reconfirmation` and preserves its prior fingerprint. Network error, rate limiting, timeout, 5xx, contract drift, or internal failure changes only the latest observation and never downgrades confirmed Token validity or account binding. A rotation-candidate mismatch rejects only that candidate and does not alter the current Credential's binding.

## 9. Shared Request Gate and Failure Behavior

### Safe transport

`UpstreamContractAdapter` uses one fixed, code/config-allow-listed HTTPS origin and the confirmed `getUserInfo` path. The `req/` evidence for this endpoint is POST JSON `{}` with the upstream `token` header and direct JSON response; it does not use the other endpoints' encrypted `item` envelope or response decryption. Require the configured origin to match the evidence task's exact host; never accept a user-supplied URL. Send with `allow_redirects=false`; any 3xx is a contract/transport failure and the `token` header is never forwarded to another host. Do not reuse legacy `backend/client.py`, which logs request/response bodies and snippets and does not disable the HTTP library's default redirect behavior. TLS verification remains enabled.

Require explicit `UPSTREAM_CONNECT_TIMEOUT_SECONDS`, `UPSTREAM_READ_TIMEOUT_SECONDS`, `UPSTREAM_TOTAL_DEADLINE_SECONDS`, and `UPSTREAM_MAX_RESPONSE_BYTES`, with `connect_timeout < total_deadline` and `read_timeout < total_deadline`. Each connect/read operation has a finite timeout. Use a monotonic total deadline, stream the response, check the deadline between chunks and before starting each next read, and stop starting reads once it is exceeded; close the response promptly. Do not promise an operating-system-level interruption at the exact total-deadline instant: a read already blocked in the HTTP/socket stack may overrun by at most its configured read-timeout bound, plus ordinary scheduling overhead. V1 does not require replacing the HTTP client, adding a thread pool, or implementing custom socket cancellation unless real tests show the existing stack cannot meet these bounds. Enforce a strict response-byte counter. Oversized bodies, redirects, TLS errors, and deadline expiry fail closed without logging body, headers, Token, or personal fields.

### Persistent shared gate

Every `getUserInfo` call passes through one SQLite-backed `UpstreamRequestGate` shared across users and Credentials. The endpoint row contains `endpoint_key`, opaque per-request `lease_owner_id` (not a user ID or Token), monotonically increasing `lease_epoch`, `lease_expires_at_utc_ms`, `next_validation_attempt_id`, `active_validation_attempt_id`, active request context (`user_id`, optional `credential_id`, operation kind, snapshot Credential version/current revision), `next_allowed_at_utc_ms`, and upstream backoff state. The context contains only internal IDs and safe version metadata, never Token, fingerprint, or personal fields, and is not exposed through user APIs. Acquire/attempt-sequence allocation and gate state changes use short `BEGIN IMMEDIATE` transactions; they never hold a DB write lock across HTTP. A permit stores its allocated attempt ID in the lease so completion records the original request order. A denied permit also allocates and observes an attempt ID without creating an active lease.

Acquire atomically allocates an attempt sequence and checks the current endpoint permit, in-flight lease, configured minimum interval, and backoff. If no permit is available, the synchronous Flask request immediately appends a `rate_limited/not_dispatched` observation and returns `429 validation_rate_limited` with HTTP `Retry-After` and JSON `retry_after_seconds`; it does not sleep and does not create a hidden background queue. A complete HTTP response releases a lease only when owner ID and epoch match. `next_allowed_at_utc_ms` and Retry-After use a monotonic maximum rule so later concurrent updates cannot shorten a backoff.

Set lease expiry to request start plus the configured total deadline and an explicit safety margin that covers at least one configured read-timeout interval plus scheduling/network cleanup overhead. Once the permit crosses the dispatch boundary, any timeout, cancellation, or incomplete response is uncertain: record `network_error`, return promptly with a retry delay, and keep the endpoint lease/backoff unavailable until the lease expiry. Do not release early just because the local caller stopped waiting. Expiry does not prove that a remote server stopped processing. If a new caller finds an expired lease, its reclaim transaction first appends a safe `network_error/stale` observation for the stored active attempt context if one does not already exist, then advances the lease epoch and may acquire a new permit if `next_allowed_at_utc_ms` also allows it. The transport stops initiating reads after its monotonic deadline and closes the response when control returns from a bounded blocking read. Because `getUserInfo` is read-only, a late response is ignored and can never write Credential state; no side effect is replayed. Any result carrying an old owner/epoch, or arriving after lease expiry even before a new owner appears, is stale and cannot release or update a newer lease. This bounds local overlap without claiming that a lease expiry cancels remote processing.

The parent architecture records an observed successful same-endpoint interval of approximately 668 ms with no observed 429/Retry-After response, but it does not identify that endpoint as `getUserInfo`. Do not apply 668 ms here unless Task 0 proves the endpoint match. The endpoint-scoped `UPSTREAM_GET_USER_INFO_MIN_INTERVAL_MS` remains a separate service gate setting; it does not determine whether token validation or account-continuity evidence is supported. If the setting is not configured, the API returns safe `503 validation_not_configured` and persists no submitted Token. No per-user, per-Credential, or per-Agent permit can be combined to evade the service limit.

Retry-After parsing is bounded and endpoint-wide. V1 accepts `delta-seconds`; it accepts HTTP-date only when Task 0 evidence requires it and the implementation uses a standard-library HTTP-date parser with timezone-aware UTC conversion. Malformed values, negative values, numeric overflow, or an unparseable HTTP-date do not directly update the gate; use configured `UPSTREAM_RETRY_AFTER_FALLBACK_SECONDS`. Add `MAX_UPSTREAM_BACKOFF_SECONDS`; validate that the fallback is positive and no greater than the maximum. Clamp every parsed upstream delay and fallback to the configured maximum before computing the deadline. A valid HTTP-date already in the past yields zero delay, after which the configured minimum interval still applies. Apply all deadlines with the existing monotonic-maximum rule (`max(existing_deadline, now + bounded_delay)`), so a later response never shortens a backoff established by an earlier response. These values are shared by all users, Credentials, and Tokens.

### Snapshot, network, and conditional write

Every validation and rotation follows the same sequence:

1. Read a user-scoped snapshot containing `credential_id`, `user_id`, `credential_version`, `current_token_revision_id`, enabled/deleted state, `requires_revalidation`, `account_binding_state`, nullable account fingerprint/key version, identity-contract version, and the active/retained key-version set (keyring epoch). Rotation also captures expected current revision and candidate Token metadata. Do not hold a SQLite write transaction during network I/O.
2. Acquire the shared gate in a short transaction and recheck ownership, expected version/revision, enabled/non-deleted state, expiry, and configured key versions immediately before defining the request in flight. Committing the permit is the dispatch boundary. If the check fails or no gate permit exists, return without dispatching.
3. Make the bounded read-only request outside the transaction.
4. Reopen `BEGIN IMMEDIATE`. Compare every snapshot field again, including owner, row version, current revision, lifecycle state, `requires_revalidation`, account-binding state/fingerprint/key/contract version, keyring epoch/active key IDs, and gate owner/epoch. For first creation or rotation, recheck that a parseable candidate `exp` is still in the future at commit time. Only a matching snapshot with a non-expired candidate may update the current Token summary, perform an allowed account-binding transition/lazy rebind, create/rotate a Credential, or clear `requires_revalidation`.
5. For a complete response, in the same final SQLite transaction append the safe validation observation, apply only the allowed Credential summary changes, update gate backoff monotonically, and release the permit only when owner/epoch match and the lease is still live. This makes applied state, observation, and lease release atomic. If the Credential snapshot is stale, record `apply_state=stale`, return `409 validation_stale`, and leave current state untouched. If the lease owner/epoch is stale or expired, never release or alter the newer lease; append a stale observation only if that attempt ID has not already been recorded during lease reclaim. A response that arrives after disable/delete/rotation cannot restore state or append ciphertext. A disable/delete committed after the dispatch boundary cannot recall the already-authorized in-flight read-only call; its result is stale and no subsequent call is allowed. The design does not claim a sent request can be recalled.

For a candidate whose account identity is confirmed, compute fingerprints in memory using the retained versions of the one fingerprint HMAC keyring. The final serialized transaction compares against same-user `confirmed` Credentials, including disabled rows, under each row's stored key version. `needs_reconfirmation` fingerprints are not duplicate-match inputs; they are used only to recover that same row's binding. Lazy rebind first compares a successful current identity under the stored key using `hmac.compare_digest`; only on a match does it compute the active-key fingerprint and conditionally update key and identity-contract versions. No raw identity value survives the request.

Failure rules:

- A candidate Token must pass read-only validation before its revision becomes current. Timeout, 429, 5xx, malformed response, or ordinary contract drift cannot change the current Token summary or revision pointer. Account-binding transitions follow the three-state rules in Section 5; a successful Token validation may be recorded while binding remains unresolved or enters `needs_reconfirmation`.
- Only an explicit invalid-Token response whose mapping is confirmed by `req` may set `confirmed_invalid`. The current four captured `getUserInfo` samples are all successful; until invalid semantics are evidenced, non-success responses remain `validation_unknown` or contract drift, not invalid.
- If account continuity cannot be proven, create a successful Token-validation Credential only as `unresolved`; do not rotate it, use it for future account-bound Jobs, or guess using username/telephone similarity.
- If encryption/decryption fails, do not call upstream or return ciphertext details; fail closed with a safe operator code.
- The gate does not retry automatically or wait in the Flask request. The user may explicitly retry after the returned gate delay. Multiple Tokens cannot bypass the gate.

## 10. UI and Privacy

The Credential page shows label, `credential_version`, enabled/`requires_revalidation` state, `account_binding_state`, separate expiry and confirmed-Token-validation states, `last_successful_validation_at_utc`, and `latest_requested_validation_attempt`. It labels whether an attempt is a current-Token check, a create candidate, a rotation candidate, or a request deferred by the gate. It explains that the latest attempt is most recently initiated by request order, not most recently completed. It can therefore show “recently initiated validation: rate limited” alongside “last successful validation: 21:03:12” without implying conflicting timestamps. A failed rotation candidate does not make the still-current Token invalid. A prior `confirmed_valid` with a later current-Token network/429/contract failure is shown as “last confirmed valid at …; latest validation attempt failed …”, never as permanently valid. A successful Token check with `account_binding_state=unresolved` is described as “Token verified; account continuity not established,” and `needs_reconfirmation` clearly blocks rotation and account-bound execution. The logged-in home shell summarizes only the user's own Token expiry and validation risks. The UI provides add, validate, rotate only when binding is confirmed, enable/disable, and soft-delete; it has no duplicate-confirmation flow.

Token input exists only in the form's memory and one API request body. Clear it on the response, cancellation, or navigation, including when a same-account conflict is returned; the user then works with the existing Credential rather than resubmitting through a confirmation dialog. Local development uses the loopback Vite `/api` proxy; deployed browser/API traffic is same-origin HTTPS. The current CORS allowlist need not add PATCH/DELETE while this same-origin constraint holds. Any future cross-origin browser deployment must extend `security.py` preflight methods and add tests before enabling it. Never put the Token in a URL, router state, local/session storage, analytics, frontend error message, or browser log. Do not return it in API responses. The UI never displays the account fingerprint, identity-contract version, or upstream `idserial`, telephone number, or username learned during validation.

The existing HTTP helper clears in-memory application Session state on protected-route 401. Therefore upstream Token invalidity must be mapped to a non-401 safe code (`422 credential_token_invalid` only after its exact response mapping is evidenced); upstream timeouts, contract drift, 429, and 5xx use non-401 codes. Frontend state tests must prove that these upstream errors preserve the application Session, while actual Session-invalid 401 continues to clear it.

Logs use field allow-lists. They may include credential ID, revision number, endpoint identifier, HTTP status class, safe validation code, duration bucket, and request-gate outcome. They must omit Token, JWT/payload, authorization headers, raw request/response, `idserial`, phone, username, fingerprint, and URL query parameters.

## 11. Acceptance Criteria

- A new migration adds Credential, immutable Token revision facts, append-only validation/audit observations, and endpoint gate tables with user-bound foreign keys, monotonic revision numbers, nullable account-binding/fingerprint fields, the three binding states, and required indexes. It does not include `validation_summary_revision_id`. Identity rows remain intact; readiness and checksum checks continue to work.
- Keyring startup tests reject empty rings, duplicate key IDs, a missing active key, noncanonical/malformed base64url, decoded keys not exactly 32 bytes, encryption/fingerprint key material reuse, and missing keys still referenced by live rows. They do not use printable-byte or fuzzy placeholder heuristics. `create_app(config)` never copies raw keyring values into ordinary Flask config, repr, or logs. Inert tombstones/historical fingerprints that are not compared do not require retired keys; `needs_reconfirmation` retains a live account-fingerprint dependency.
- A valid synthetic Token can be validated by a synthetic adapter fixture; only authenticated ciphertext and safe metadata persist. Tests/logs/API/frontend state contain no Token, JWT payload, `idserial`, phone, username, fingerprint, or raw response.
- `exp` tests reject bool, NaN/Infinity, unsafe types, range overflow, and non-millisecond-exact numeric values; these become `expiry_unknown` except a valid expired NumericDate, which is blocked before network dispatch. Input tests cover empty/control/overlength Token and invalid label boundaries.
- The adapter contract test asserts POST JSON `{}`, exact allow-listed HTTPS origin/path, `token` header, direct JSON response, `allow_redirects=false`, and no item encryption/decryption for `getUserInfo`. It validates HTTP status plus endpoint-specific JSON success/message/resultData. Unknown response shapes fail closed.
- Task 0 reports `token_validation_capability` and `account_continuity_capability` independently. If the successful `getUserInfo` request/response contract is supported but account continuity is not, tests prove a valid Token can create an `unresolved` Credential only when the user has no other non-deleted Credential; it can then be revalidated, disabled, and deleted, while rotation, duplicate matching, and account-bound execution remain blocked. A Token-success response with no usable identity follows the same unresolved rule; if another Credential exists and cannot be safely compared, creation conflicts without persisting the candidate. If continuity evidence is sufficient, a successful current-Token validation can establish `confirmed`; evidence records observed samples and explicitly leaves global uniqueness/future permanence unproven. Task 0 separately records invalid-Token response and endpoint timing evidence. No live upstream call is made in automated tests or without separate explicit authorization.
- Repeated `/validate` calls do not mutate semantic Token revision fields or a second validation-summary revision pointer, because no such pointer exists. A transient timeout/429/5xx/contract drift updates the latest requested attempt only, preserves previous confirmed Token validity, account binding, and last success, and the UI distinguishes request order from completion time.
- Validate and rotate race tests force concurrent version/current-revision changes, disable, delete, re-enable, and fingerprint-key changes between request snapshot and response. Stale results cannot overwrite current state, append a revision, restore enablement, or clear `requires_revalidation`; candidate `exp` is rechecked in the final transaction.
- Token validation without continuity evidence creates an `unresolved` Credential and does not persist an account fingerprint. A later successful validation under an approved identity contract may promote it to `confirmed` only if same-user uniqueness holds. A confirmed current-Token identity mismatch moves the Credential to `needs_reconfirmation`, preserves the old fingerprint, and never silently rebinds; transient errors do not change binding. Reconfirmation succeeds only on a constant-time match under the current approved contract. Disable/enable leaves binding state unchanged; enable independently sets `requires_revalidation`; soft delete clears the active fingerprint and bars binding use.
- Only `confirmed` Credentials may rotate. A candidate Token for a different account is rejected without changing the current binding; unresolved or needs-reconfirmation rotation is rejected before dispatch. A same-account rotation appends one semantic revision and atomically advances pointer/summary. A candidate matching the current Token returns `token_already_current` without a request or new revision. Historical Token reuse is not rejected in V1 absent protocol evidence.
- At most one non-deleted Credential per same-user confirmed upstream account is allowed, including disabled rows. Same-account create returns a safe `409 credential_account_already_configured` recommending re-enable or rotation; no duplicate-confirmation payload, UI, set/version handshake, or override path exists. Two concurrent creates serialize so one succeeds and the other conflicts. A same-user unresolved/needs-reconfirmation row blocks creation of another Credential until it is confirmed or soft-deleted, without matching its fingerprint; if continuity capability is unavailable, any existing non-deleted row blocks a second creation. Promotion/reconfirmation that discovers an existing same-user confirmed match is blocked and retains the original unresolved/needs-reconfirmation state. Different users may independently bind the same upstream account; no cross-user UNIQUE or product lookup exists, and errors never disclose another user's match.
- Fingerprint rebind tests cover v1 Credential with active v2, successful old-key continuity then atomic v2 rebind, mismatch preservation, `needs_reconfirmation` recovery, and retention of v1 while any non-deleted Credential references it. Candidate duplicate checks compare under every retained key version against same-user confirmed Credentials only. HMAC-key removal is rejected while referenced; inert tombstone metadata alone does not keep keys live.
- Re-enabling a disabled Credential sets `requires_revalidation`; old successful history cannot authorize calls. Only a successful current-revision validation or validated same-account rotation clears the flag. Deletion clears every revision ciphertext/nonce/tag and account fingerprint in active rows and records safe clear metadata; tests do not claim physical SQLite/WAL/backup erasure.
- Gate/transport tests verify finite connect/read timeouts, `connect_timeout < total_deadline` and `read_timeout < total_deadline`, streamed byte limits, total-deadline checks between chunks, bounded single-read overrun without claiming exact blocking-read interruption, lease expiry covering total deadline plus margin, TLS verification, redirect rejection, and shared cross-Credential Retry-After handling. Retry-After tests cover delta-seconds, HTTP-date only when enabled by evidence and parsed by the standard library, malformed/negative/overflow/unparseable fallback, maximum clamp, and monotonic max behavior. They also cover immediate 429 plus safe retry delay when no permit exists, no Flask sleep/hidden queue, owner/epoch release, stale-owner fencing, uncertain timeout retention, and crash recovery after lease expiry plus safety margin.
- Attempt-order tests verify the gate allocates `validation_attempt_id` before permit/no-permit resolution; a later gate-denied observation stays `latest_requested_validation_attempt` even if a slower earlier read-only response completes afterward. Its start/completion times are present; the UI can show it as the latest initiated attempt while separately showing a later-completing last successful validation. Gate-denied observations do not mutate Credential version/confirmed state. Lease-reclaim tests append a safe stale observation; a late old owner cannot release a newer lease or overwrite that observation.
- Frontend tests prove upstream Token invalidity uses a non-401 code and does not clear the application Session, while Session-invalid 401 still does; same-origin Vite proxy supports PATCH/DELETE without changing the current CORS allowlist. Cross-origin use is not enabled until preflight methods are explicitly reviewed and tested.
- Cross-user Credential IDs return the same non-disclosing 404 as missing IDs. All Credential API SQL binds current `user_id`. Tests use temporary SQLite and synthetic fixtures only; they do not load `.env`, read raw req files, print secrets, or call real upstream services.
- Tailscale, BookingPlan, BookingJob, Worker, Agent, payment, booking UI, and real booking/payment requests are not added in this phase.

## 12. Handoff to Implementation Planning

After this design is approved, the separate implementation plan should preserve Task-sized, test-first commits on a short-lived feature branch/worktree based on `main`, with final rebase, full backend/frontend/build acceptance, fast-forward merge, cleanup, and a milestone tag. Task 0 is read-only: inspect only local req captures and official frontend source in memory, extract allow-listed method/path/header/body-key and response-shape evidence, and never output raw values or issue a live request. It produces two independent outcomes:

- If the request/response facts and recorded success support `token_validation_capability`, Credential Token read-only validation may be implemented even if account continuity remains unresolved. Inability to prove cross-account global uniqueness or permanent future stability is recorded as an evidence limit, not a blocker for token-only Credentials.
- `account_continuity_capability` is enabled only if the observed evidence supports an allow-listed field as a same-account continuity signal.
