## 2026-10-21 系统性优化完成

本节为本轮最终实现与验证记录。下文“早期抽样”和“本轮开始前的回归证据”保留历史，不能代替本节验收。

### 实际问题与修改

- 新一轮相对日期原来仍用对话开始日期，跨午夜会错一天；现在按本轮业务日解析，历史已确认 ISO 日期保持不变。
- 同字段只能输出一条更新、且 evidence 只检查子串，无法可靠处理复合增删、范围端点误抽和错误操作；现在允许顺序 Typed Delta，并独立核对原文与日期、时段、场地、时长组、操作及顺序。同一字段有语义错误时不部分应用，保留原确认事实并追问。
- 日期更新会对照本轮完整原文处理否定、并列选择和纠正，不能把“不是26日，改成28日”中的26日保存或安排自动任务。1小时与2小时的时段、场地、清空和重叠确认也核对原文组别；模型写错目标组时不改事实，并回到用户实际提到的组继续确认。
- 增加有界的局部编辑、取消与整轮事务撤销。修改历史字段后恢复原动态焦点；取消只恢复局部字段，不覆盖期间更新的无关事实；唯一指代才应用，否则澄清。
- 无效时段、3小时冲突、场地范围及重叠歧义持续保留。修改相关字段后重新校验，不解除独立歧义；停用时长组不污染另一组。
- READY 改为单轮可预览状态；同一聊天可继续修改和问答。未发送的修改禁用旧预览保存，普通回答也显示在历史中。
- 普通问答不消耗业务字段重试，相同候选的答疑复用非权威复核缓存。Provider 异常不提交半成品，输出截断作为独立 Provider 错误处理，不再当作 JSON 格式错误重试。
- 今天及未来日期可预览、保存；过期日期不能重新保存。预览和保存共用目标日前两天07:30的资格判定，严格按毫秒判断；保存时按当前时间重算，幂等保存也不能沿用旧资格。该信息不创建任务，不改变执行器或非空队列的付款授权规则。

### 职责与状态

`queue_graph` 保持单轮短图；`queue_turn` 校验 Typed Delta 协议；新增 `queue_grounding` 核对证据语义并拦截明显遗漏的非法信息；新增 `queue_dialogue` 管理局部编辑、取消、撤销；`queue_updates` 应用事实；`queue_slots`/`conversation` 校验领域约束并推导下一动作；`planning` 协调一次模型理解和必要的预览复核。

v5 JSON 沿用现有 SQLite CAS 会话表，不增加数据库或第二套 checkpointer。保存 canonical draft、pending_edit、dialogue_focus、next_action、事实来源、未解决证据、撤销事务和非权威复核缓存；模型上下文不携带撤销快照。v2/v3/v4 按兼容路径恢复规范化事实。权限、重放幂等、CAS 和敏感历史拦截继续由服务端保证。LangGraph 保持0.2.60，没有新增依赖、ReAct 或多Agent。

## 本轮开始前的设计诊断

早期实现每轮已将对话历史、工作流、槽位和硬规则交给模型。但当时两处结构使模型作用被削弱：

1. 模型返回结构化更新后，旧实现会把更新编译成中文，再由 `queue_draft.fold()` 的正则和词法规则重新解释。一个意思经过模型、文本编译、规则解析三次转换，容易出现“模型说已记录，槽位没更新”或指代丢失。
2. `eligible_fields()` 原来只返回固定顺序中的第一个缺口。模型看见完整流程却无法真正建议下一步，`next_field` 实际上没有选择空间。

最近 zhl 对话成功生成了 32 项预览，说明完整路径可用；它不能证明模型在协调流程，也不能覆盖纠正、短回答、规则问答、超限修复等路径。

## 设计原则

- 把 Agent 设计成“模型编排 + 领域校验”的混合系统。LangGraph 的 agent/workflow 指南区分固定代码路径和动态模型决策；这里需要动态理解、归纳、追问与路由，同时保留确定性的预约事实校验。
- 每轮让模型从整段对话和当前状态判断：用户是在补充、纠正、提问、混合表达、取消，还是要求执行；抽取所有明确事实；选最值得确认的下一项；生成简短答复和单项追问。用户问“我确认了什么/为什么还要回答”时，基于已验证槽位与历史答复解释当前进度，不限于复述静态规则。
- 模型只能提出事实更新和下一动作。服务端独立校验更新、重新计算槽位、检查候选，任何“已就绪”声明都不能代替验证。
- 状态保存规范化事实和来源，不保存模型编译出的伪自然语言。提示词从状态按需构造；历史事实不靠重复解析用户原文恢复。
- 流程作为一个结构化 policy 一次传入模型；避免在提示词、解析器、状态机和 UI 里分别复制不同的优先级表。

## 模型决策协议

单次模型调用返回严格结构化的 turn decision：

- `intent`: `queue | execution_request`
- `kind`: `answer | question | mixed`，描述本轮对话类型。
- `updates`: 对已知字段的 `set / replace / add / remove / clear / confirm` 提议；每项带最新用户原话证据。
- 同一字段允许按原文顺序提交多个 update，例如先 remove 再 add；服务端顺序应用并按整轮记录撤销事务。时段 update 最多12项；状态快照容量按 21 轮 × 每轮 12 个时段封顶。
- `reply`: 回答用户确实问到的内容；问题类消息必须非空。
- `next_field` 与 `next_question`: 模型在多个当前活动缺口中结合历史和用户偏好选一项，不重复已确认字段；服务端校验依赖并记录最终选择。
- `unresolved`: 模型指出的歧义和对应原文，不自行猜值。

模型上下文由一条服务器生成的状态 JSON 和按时间顺序排列的 user/assistant 历史消息组成。状态 JSON 提供对话开始日期、当前业务日期/时区、当前待答问题、规范化槽位、字段依赖、候选数量和预约规则；历史用户原话与助手答复投影以独立消息传入，带有“本轮用户原文”标记的消息是当前输入。助手投影保留每轮问题、答复、校验摘要和路由，不把多轮文字合并成一条 Provider 消息；对话历史不因单条 32 KiB 消息上限而压缩。单条 user 输入总长受 4000 字符/12000 UTF-8 字节约束，每条消息仍受 32 KiB 和 64 条上限约束。历史文字均视为不可信内容，不能覆盖系统策略或当前已校验状态。

## 服务端职责与最终边界

1. 校验模型输出的 schema、字段白名单、操作、证据位置和长度；拒绝未知字段及未引用的值。
2. 将 updates 应用到候选状态副本；在整轮通过验证前不持久化。
   时段更新分别保留有效和无效区间；`add` 不会清掉未解决的错误，`remove` 只解除匹配的无效区间，`replace` 才整体替换。
3. 以业务验证器核对：日期非过去；候选时段完整且为 1/2 小时、整点、09:00–22:00；场地 1–10；两组独立；重叠要明确解决；候选不超过 32 项。
4. 根据更新后的验证状态确定是否追问、升级或生成预览。模型选中的字段必须仍是当前活动且未解决的字段；越过未完成硬依赖时回退到下一个有效缺口并记录差异。工作流优先级只用于模型选择，不伪装成硬验证规则。
5. 对真正缺失的字段，采用模型提供的自然问法；对无效或歧义字段，追问由服务器的校验结果生成，模型不能把错误值描述为有效。
6. 只有有效状态才能生成候选预览；只有用户点击保存才写队列。Agent 不持有查询、预约、下单、支付或创建任务的工具。

## LangGraph 单轮流程

`load_state → build_context → interpret_intent_and_next_field (LLM) → apply_to_candidate → validate_and_reconcile → ask / answer / preview / refuse → persist_response`

需要补充或纠正时，每轮调用一次模型解释上下文；只有队列字段全部通过服务端校验、进入预览时，才额外调用独立复核模型生成非权威提示。复核不能改候选或把无效状态变成有效。两类调用各自在格式错误时最多重试一次。Provider 超时/限流明确报告，未知错误不吞掉。DB 对话版本用于并发保护；候选状态只在成功解释并校验后提交。

## 状态模型

- `facts`: queue mode、date、1h/2h time windows、courts、overlap decisions。
- 规范化 Draft 保存事实值和状态；每轮来源 evidence 由 response_history 的 turn trace 保留。拒绝或歧义保留为 unresolved，不静默丢弃。
- 同一条消息里的有效与无效时段分别保存；追加不会解除已有无效项，删除只清除匹配区间，替换才能整体重列。无效区间容量与最大对话轮数对齐。
- `turns`: 原始用户消息、助手问题/答复、已验证的更新摘要、模型建议与服务端最终路由。
- `conversation_start_date` 仅保留为历史锚点；最新输入的“今天/明天/后天”均按该轮 `current_business_date` 解析。已确认日期保存为 ISO 日期，不随之后跨午夜重算。
- 旧对话仅在第一次恢复时兼容旧字段（`more_2h`、`want_1h` 等），以最后保存的已校验槽位快照校正旧解析结果，并重置旧字段的重试计数；首轮响应会保存 v5 规范化 Draft，后续不再重放旧规则。
- 旧快照标记为无效/歧义的启用字段继续阻塞队列；旧快照标记为未填写的场地会清掉旧解析器误读出的数字，避免把时间范围当作场地号。
- Provider 调用前检查完整用户轮次和恢复出的助手历史中的可识别 Token、API Key 与密码格式；命中则拒绝本轮，避免把旧消息里的敏感值再次发给模型。
