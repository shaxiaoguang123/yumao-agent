## Global Constraints

- Keep Flask API + Vue + SQLite + lightweight Worker; do not add Redis, Celery, PostgreSQL, multi-node scheduling, or microservices.
- All authenticated domain-resource SQL reads and writes must bind the current `user_id` in the database query. This phase has no booking-domain resources; session resolution joins the hashed Session row to its user, and admin operations apply explicit role and target checks in SQL. Carry this rule into every later user-owned resource endpoint.
- Use a revocable server-side Session. The browser cookie contains only a random opaque Session ID; SQLite stores only its hash. A still-valid bearer-style cookie that is copied in full remains usable until expiry or revocation; V1 does not claim to detect copying and does not add device binding or another Session architecture. Login rotation may revoke a valid prior Session only when it belongs to the same target user; logging in as another user replaces the browser cookie without revoking the prior user's server-side Session.
- Passwords use versioned scrypt hashes; invitations are high-entropy, single-use, expiring, and redeemed atomically.
- Cookie-authenticated mutations require a session-bound CSRF token and configured Origin/Referer validation. `CSRF_HMAC_SECRET` is canonical unpadded base64url representing at least 32 CSPRNG-generated bytes; decode strictly and fail fast on missing, invalid, weak-placeholder, or short values. AppSettings stores only decoded bytes with repr disabled. Do not persist CSRF tokens, Session IDs, or material that can recover a Session ID.
- Do not log passwords, password hashes, Session IDs, CSRF tokens, the CSRF HMAC secret, invitation codes, cookies, Authorization headers, source IPs, or request bodies.
- Keep `.env`, `req/`, runtime logs, databases, extracted bundles, binaries, and generated frontend assets out of Git.
- Tests use temporary SQLite databases and synthetic data only. They do not load `.env`, read `req/`, or call a real upstream service.
- Migrations run from one explicit command/process. Flask app startup checks schema readiness and fails fast; it never applies migrations implicitly. Do not add OAuth, WebAuthn, device binding, JWT app login, persistent client auth tokens, complex RBAC, public registration, Tailscale deployment, or real booking calls in this phase.

## Review Focus

- Invitation reuse and concurrent redemption must create at most one account; test sequential and simultaneous redemption.
- Session expiry, logout/revocation, password-change revocation, account disable, and Session rotation must invalidate old Sessions; do not test that a copied but still-valid opaque cookie is detectable.
- Login, registration, and cookie-authenticated mutations must reject disallowed Origin/Referer or missing/invalid CSRF as applicable; rotation must invalidate the prior Session/CSRF pair.
- Every connection must set row factory, foreign keys, and the explicit busy timeout; migration failure must roll back schema and version together while preserving prior data.
- Independent username and source-IP login buckets, the last-active-admin rule, bootstrap-admin concurrency, and two-user Session isolation must be tested.

## Task 2: Add SQLite Connection Policy, Atomic Identity Migrations, and Schema Readiness

**Files:**

- Create: `backend/db.py`
- Create: `backend/migrate.py`
- Create: `backend/migrations/0001_identity.sql`
- Modify: `backend/app.py` to enforce readiness.
- Modify: `backend/tests/test_app_factory.py` for migrated and unready database startup cases.
- Test: `backend/tests/test_db.py`

**Interfaces:**

- `connect_database(database_path: Path, busy_timeout_ms: int) -> sqlite3.Connection` sets `row_factory=sqlite3.Row`, `PRAGMA foreign_keys=ON`, and the supplied busy timeout on every connection. `db.py` does not read hidden/global settings.
- `migrate_database(database_path: Path, busy_timeout_ms: int, migrations_dir: Path | None = None) -> None` sets WAL before migration transactions, bootstraps migration metadata separately, and runs each numbered migration in its own explicit transaction. `migrations_dir` defaults to the repository migration directory and is injectable for isolated rollback, parser, and checksum tests.
- `schema_migrations` records `version`, `filename`, SHA-256 `checksum` of the exact migration file bytes, and `applied_at_utc_ms`. Before any database-changing setup (including WAL mode or metadata bootstrap), the runner verifies every already-applied version/filename/checksum against the current repository files; mismatch raises `MigrationHistoryMismatch` without changing the database. Applied migration files are immutable; later changes use new versions such as `0002_xxx.sql`.
- For each migration: execute `BEGIN IMMEDIATE`, run its SQL statements individually on the same connection, insert its version/filename/checksum/applied timestamp, then `COMMIT`. Any error triggers `ROLLBACK`, so schema/data changes and migration metadata are atomic. Parse statement boundaries with `sqlite3.complete_statement()` or an equivalent SQLite-aware parser; never use `sql.split(';')`. Migration files must not contain top-level transaction-control statements (`BEGIN`, `COMMIT`, `ROLLBACK`, or `SAVEPOINT`); `BEGIN ... END` inside a trigger is valid. Enforce transaction-control rejection with a SQLite authorizer while executing migration statements, not text matching; disable the authorizer before the runner's own `COMMIT` or `ROLLBACK`. Do not use `executescript` unless its transaction behavior is proven to preserve these exact boundaries.
- `check_schema_ready(database_path: Path, busy_timeout_ms: int, required_version: int, migrations_dir: Path | None = None) -> None` raises a clear `SchemaNotReadyError` if the file is missing, `schema_migrations` is absent, the applied version is older or newer than supported, required identity tables/columns are missing, or `PRAGMA foreign_key_check` reports violations. It is read-only and never creates or repairs a database, updates checksums, or applies migrations. It also verifies every applied migration's version, filename, and SHA-256 checksum against repository files and raises `MigrationHistoryMismatch` on any difference.
- `CURRENT_SCHEMA_VERSION = 1` is the required V1 identity version. `create_app` calls `check_schema_ready(database_path, busy_timeout_ms, CURRENT_SCHEMA_VERSION, migrations_dir)` before registering/serving the application. Tests and local setup explicitly run migrations before constructing the normal app.
- `python -m backend.migrate` is the only migration entry point and passes settings explicitly; app startup never migrates.

## Task 3: Implement Password, Session, Invitation, and Rate-Limit Services

**Files:**

- Create: `backend/auth/__init__.py`

- Create: `backend/auth/sessions.py`
- Create: `backend/auth/invitations.py`
- Create: `backend/auth/rate_limit.py`
- Test: `backend/tests/test_auth_services.py`

**Interfaces:**

- `normalize_username(username: str) -> str` returns Unicode NFKC → trim → casefold for comparison only. The original display value remains in `users.username`.
- `hash_password(password: str) -> str` returns a versioned scrypt hash; `verify_password(password: str, stored_hash: str) -> bool` safely rejects malformed/unknown versions and uses constant-time comparison.
- `UserSummary` and `SessionContext` are frozen dataclasses in `backend/auth/types.py`. `UserSummary` contains `user_id`, safe display `username`, and `role`; `SessionContext` contains the summary and `csrf_scheme_version`, never raw Session material.
- Services receive explicit `database_path` and `busy_timeout_ms`; `SessionService` additionally receives `csrf_hmac_secret`. No service reads hidden global config.
- `SessionService.create(user_id: str, now_utc_ms: int) -> tuple[str, str]` returns the raw opaque Session ID once and its CSRF token while storing only the Session-ID hash and scheme version.
- `SessionService.rotate(old_session_id: str | None, target_user_id: str, now_utc_ms: int) -> tuple[str, str]` opens one `BEGIN IMMEDIATE` transaction, revokes the old Session only if its hash resolves to an unexpired, unrevoked Session owned by `target_user_id`, and creates the new Session. If the old Session is missing, expired, revoked, malformed, or belongs to another user, it is not revoked; a new Session is still created. The new ID yields a new CSRF token.
- `SessionService.resolve(session_id: str, now_utc_ms: int) -> SessionContext | None` rejects missing, expired, revoked, disabled-user, and malformed Sessions.
- `SessionService.revoke(session_id: str, now_utc_ms: int) -> bool` revokes a matching Session. Password-change and user-disable transactions revoke all Sessions for the user.
- `SessionService.csrf_token_for(session_id: str, scheme_version: int = 1) -> str` computes HMAC-SHA256 with the decoded server `CSRF_HMAC_SECRET` over the version-1 message `b"csrf-v1:" + session_id.encode("utf-8")`, then URL-safe-base64 encodes the digest. Persist only the Session hash and scheme version; never store recoverable Session material or a CSRF token.
- `SessionService.verify_csrf` uses `hmac.compare_digest`. Login rotation creates a different Session ID and CSRF token; the old Session and old CSRF pair both fail.
- `InvitationService.create` returns a one-time high-entropy code and stores only its hash. `InvitationService.redeem(code, username, password_hash, now_utc_ms) -> UserSummary` atomically consumes an unused/unexpired code and inserts one account, checking uniqueness by `normalized_username` while retaining display `username`.
- `RateLimitBucket` specifies event type, bucket type/key, limit, and rolling-window seconds. `RateLimitService.check_and_record(event_type: str, buckets: Sequence[RateLimitBucket], now_utc_ms: int) -> RateLimitDecision` runs one `BEGIN IMMEDIATE` transaction: query every bucket for `attempted_at_utc_ms >= now_utc_ms - window_seconds * 1000`, decide all buckets, then either record all bucket attempts or none. If any bucket is at its limit, return denied and compute each blocked bucket's `Retry-After` from its earliest still-valid attempt leaving that inclusive window (`timestamp + window_ms - now + 1 ms`, rounded up to whole seconds); return the maximum across blocked buckets, using the same transaction snapshot. Prune expired rows in that transaction.

**Interfaces:**

- `GET /api/auth/session` returns `{authenticated: false}` when unauthenticated, or the minimal current-user summary and session-bound CSRF token when authenticated.
- `POST /api/auth/register` accepts the invitation code only as a JSON request-body field, consumes it, and creates an account with HTTP 201; the new user then signs in through `/api/auth/login`. It never accepts a role/admin flag or reads the code from a URL, query, fragment, router state, or headers. Duplicate checks use `normalized_username`; responses return only the retained safe display `username`.
- `POST /api/auth/login` applies independent normalized-username and source-IP rolling-window buckets, with the optional pair bucket as an additional limit, before any scrypt verification. It verifies credentials, rotates a supplied prior Session only when it belongs to the successfully authenticated target user, and sets an HttpOnly cookie containing only the new opaque Session ID with Max-Age equal to the server-side Session lifetime. A prior Session belonging to another user is left valid server-side; the new Set-Cookie only replaces this browser's cookie.
- `POST /api/auth/logout` returns 204 only after revoking the server-side Session. If the Session is already absent, expired, or revoked, return 401 with an explicit `session_invalid`/`session_expired`/`session_revoked` code that proves it is no longer usable. A client must not interpret network/5xx/ambiguous responses as confirmed logout.
- `POST /api/auth/change-password` requires the current password and CSRF token, saves a new scrypt hash, revokes every Session for that user in one transaction, and clears the current cookie.
- `POST /api/admin/invitations` is admin-only and returns the invitation code exactly once; SQLite stores only its hash.
- `POST /api/admin/users/{user_id}/disable` is admin-only. In one `BEGIN IMMEDIATE` transaction it rechecks that the actor is an active admin, forbids disabling the current actor, forbids disabling the last active administrator, disables the target, and revokes all target Sessions. Return a clear conflict response for self-disable/last-admin violations. This prevents concurrent admin operations from removing the last active admin.
- `create_first_admin(database_path: Path, busy_timeout_ms: int, username: str, password_hash: str, now_utc_ms: int) -> UserSummary` is the CLI's atomic bootstrap operation. `python -m backend.cli create-admin --username <name>` prompts for the password with `getpass`, never accepts a password argument, and creates the first administrator only if no administrator row exists. Checking for an existing administrator and inserting the first one occur in one `BEGIN IMMEDIATE` transaction. Hash the password before acquiring the write lock.
- `require_session`, `require_admin`, and `require_csrf` are request guards. Every mutation validates configured Origin/Referer; login and registration require allowed Origin/Referer before a Session exists; authenticated cookie mutations also validate `X-CSRF-Token`.
- Login and registration use `REMOTE_ADDR` only; do not trust forwarded headers in this plan. Every login attempt uses both normalized-username and source-IP rolling buckets (pair bucket is optional additional defense); registration uses at least the source-IP bucket before validating the invitation. On any bucket denial return HTTP 429 and `Retry-After` using the longest remaining blocked window. Thresholds come from `AppSettings`, not user input. Limit checks and all bucket records are atomic; if any bucket blocks, none of the request's bucket attempts are partially recorded.
- Successful login/session responses use `{authenticated: true, user: {user_id, username, role}, csrf_token}`; failed login is generic 401 with `invalid_credentials`, and never distinguishes a missing username from a wrong password. Protected-route Session failures use an explicit Session-invalid code; invalid/expired/redeemed invitation is generic 400, forbidden access/CSRF is 403, self-disable/last-admin conflict is 409, and rate limiting is 429 with `Retry-After`. Never return Session IDs or password hashes.

**Interfaces:**

- The HTTP helper sends `credentials: 'include'` on all requests and attaches the in-memory CSRF token to cookie-authenticated mutations. It classifies errors: a 401 from a protected route or explicit `session_invalid`/`session_expired`/`session_revoked` response clears in-memory auth; login's `invalid_credentials`, 403, 429, 5xx, timeout, and network errors do not imply logout and do not clear it.
- The Session store keeps only the safe user summary and CSRF token in memory. `refresh` sets authenticated/unauthenticated only on a definitive response; transient 403/429/5xx/timeout/network failures set a retryable unavailable state and preserve existing in-memory auth. `login` sets state from success. `logout` clears state only on 2xx or explicit proof the server Session is already invalid/expired/revoked; all ambiguous failures preserve state, mark logout unconfirmed, and show `退出状态未确认，请重试`. No Session ID, CSRF token, password, or invitation code is written to localStorage/sessionStorage.
- The router provides login, invitation registration, authenticated home, and account/password-change routes. Its guard awaits the initial refresh and redirects only after a definitive unauthenticated result. A temporary refresh/network error does not cause an infinite redirect to login; it allows the requested route to render a retryable unavailable state.
- `InviteRegisterView` requires manual invitation-code entry. It never reads an invite from URL query/fragment/path, router state, localStorage, or sessionStorage; the code exists only in form memory and the body of the single registration POST, then is cleared after completion.
- Vite proxies `/api` to the local Flask server; production origin validation remains server-side.
